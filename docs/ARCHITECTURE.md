# Architecture and product behavior

execs is a Windows + Linux desktop companion for Team Fortress 2 (Tauri 2, Rust core, React/TypeScript UI). It keeps a player's whole customization surface as named **profiles** and switches between them while the game is closed. This is the public product specification for contributors. Durable behavior belongs here; setup and contribution rules live in [CONTRIBUTING.md](../CONTRIBUTING.md), and release procedure lives in [RELEASE.md](RELEASE.md).

## Repo

The 0.2.0 qualification record is [release-0.2.0-readiness.md](release-0.2.0-readiness.md). On September 27, 2026 the owner decided that Inventory ships in 0.2.0, and it was published in v0.2.0 that day.

```
apps/desktop/            Tauri app (the product)
  src/                   React UI: one file per pane, lib/ (pure logic + tests), hooks/, components/ui/
  src-tauri/src/         Tauri crate `execs`: commands/ (IPC), net.rs, *_fetch.rs, gamebanana.rs, hud_stats.rs
  src-tauri/core/        `execs-core`: everything that touches disk, no Tauri/WebKit
packages/cfglint/        Source cfg parser/linter (TS), used by the Files pane
tools/promo/             Remotion promo video, README captures and release graphics; outside the pnpm workspace (`pnpm install --ignore-workspace`)
docs/media/              README screenshots, the promo MP4 and its poster, release announcement graphics
docs/RELEASE.md          Public vs dev, versioning, cadence, ship checklist
CHANGELOG.md             User-facing notes; the release workflow reads this
.github/workflows/       ci.yml (frontend, rust-linux, rust-windows), release.yml (tag → draft → verify → publish)
```

Commands: `pnpm install`, `pnpm desktop:dev` (Tauri), `pnpm dev` (browser only, fixture data via `?preview=<state>`; states in `src/lib/preview.ts`), `pnpm test`, `pnpm check` (biome), and for Rust `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace --locked` with `--manifest-path apps/desktop/src-tauri/Cargo.toml`. CI runs all of these; keep them green. `.npmrc` `node-linker=hoisted` is required on Windows. Vite defaults to port 1420 (`EXECS_DEV_PORT` moves it; `tauri.conf.json` `devUrl` must match). Plain `package.json` scripts only; source and cfg fixtures use LF (`.gitattributes`), while archived CI evidence retains its original bytes for provenance checks.

## Architecture

- Inventory is an account pane in every build; the owner decided on September 27, 2026 that it ships in 0.2.0, so release builds show it and run its native reads, reviewed operations and helper entry points like debug builds. It reads the signed-in Steam backpack and supports reviewed live layout changes, four metal conversions and single-item deletion. Operations use an isolated bounded child process, exact account/capacity/raw-item baselines (Steam's cache version advances on each connection without item changes, so it is not compared; the helper binds confirmation to a cache newer than the one it read just before sending), native single-use review tokens, installed-schema eligibility and a durable account-owned intent journal before any send. The helper sends one mutation only, then checks response/events and a complete newer cache. A timeout or ambiguous result stays pending across restart; Reconcile reads current state and never replays a mutation. Old direct Apply/Craft IPC paths refuse; native operations require prepare/execute. Automated and agent checks did not move, consume or delete live items. Owner-reported live crafting feedback and its qualification limits are recorded in [release-0.2.0-readiness.md](release-0.2.0-readiness.md).
- Inventory snapshots load on first focused use, after TF2 closes and from the header's Refresh, never on a timer: each read runs the helper with TF2's Steam app id, so Steam briefly shows the player in TF2, and the About panel says so. Launch TF2 waits behind a read in progress through the shared write gate. Reads do not overlap and pause while hidden, unfocused, busy, drafting or in-game; failed connections back off from 30 seconds to five minutes. Same-account refreshes preserve browsing and artwork, account changes reset browsing, and failed refreshes keep explicitly stale snapshots. Drafts, favorites/protection, saved searches/layouts and operation history belong to the Steam account, never a customization profile. Favorites protect items from moves and consumption. Draft Undo never reverses a completed Steam operation.
- Inventory uses ten-column by five-row 50-slot pages with compact artwork, Ctrl/Shift selection, drag/drop, wrapping pages and held-drag page navigation. Holding one item or a selected group over either arrow turns pages every 650 ms until leaving or ending the drag; the source stays mounted and paging does not scroll the arrow away. Name/quality/type sorting packs the whole backpack into actual draft slots, leaves protected items fixed, supports Undo/Redo and uses the existing reviewed Steam layout operation, bounded to 10,000 moves to cover a full supported backpack. Search filters never sort or move items; clear filters before dragging. Legacy saved-search sort values are ignored. Inspect, Craft and Delete open on demand from a sticky footer that also holds the selection, favorite/protect toggles and the pager; there is no permanent detail sidebar or Arrange mode selector. One toolbar row holds search, Quality and Sort menus (no native selects), Undo/Redo (also Ctrl+Z / Ctrl+Y), Review changes and a More menu with selection shortcuts, Move selected to… (page/slot fields), Reset draft, and one tabbed dialog for saved searches, layouts and history. Drags dim the carried items, preview their exact landing slots, refuse invalid targets with the reason and fill the held page arrow over 650 ms. Page turns slide in their direction and layout changes (sorts, Undo/Redo, dialog moves) slide items to their new slots; reduced motion removes this. Craft and Delete close on a result and report it in the footer. Craft selected resolves only plain tradable metal to one supported recipe and reviews exact IDs/output; deletion requires exactly one selected eligible item and irreversible confirmation. The separate labeled browser fixture simulates these operations without Steam. Jengerer's Item Manager inspires the interactions and is credited; its unlicensed code/assets are not reused.
- Inventory art prefers Valve's own renders: `steam_items_fetch.rs` reads the signed-in player's public inventory descriptions from `steamcommunity.com/inventory/<id>/440/2` (context 2 asset ids are item ids) and 192/360 px PNGs from `community.akamai.steamstatic.com/economy/image/`, both pinned `RemoteSource`s. TF2 draws painted weapons, war paints and kits as live 3D renders that installed files cannot reproduce; Valve's images are those renders. Descriptions refresh at most every 10 minutes, missing items retry after 45 s, a 429 backs off 3 minutes, and a private inventory reports that rather than failing. Descriptions and images cache under `<data dir>/inventory-art/` (a Downloads storage group). This is presentation only: the GC snapshot stays authoritative, Steam text never enters an operation baseline, and every failure falls back to installed art.
- Installed metadata/art is read in bounded batches and remains the fallback. Quality borders, names, kit/fabricator targets, wear and effect labels use bounded attributes and installed metadata. Without Valve's render a war paint pairs the item icon with a pattern swatch and says so in Inspect; a kit draws its target weapon on the kit. Patterns up to 4096 px and 32 MiB decode from a small mip; other oversized optional art is omitted per item.
- Names follow TF2: a Name Tag shows in quotes with the original full name beneath (Valve's market name, else quality plus installed name), and description tags show in quotes on hover and in Inspect and are searchable. Inspect is a centered TF2-style panel (art, name in quality colour, type line, Valve's coloured description lines, slot); item numbers are not shown.
- Craft selected offers every recipe a single-kind metal selection supports, in order combine, random hat, smelt, with a choice only when there is more than one. A selection runs as whole crafts in slot order (up to 100 per review), each prepared from the previous confirmed backpack; the first refusal or unknown result stops the batch. Metal crafting requires both the known conversion's explicit recipe index and exact enabled installed recipe criteria; a schema hash binds preparation to execution. The random hat is Valve's premium-only recipe 6 (three Refined Metal, output `craft_class` hat): native review refuses free accounts (a 50-slot backpack), sends the sorted list of installed hat definitions, and the helper accepts only one new item from that list. A confirmed hat opens a reveal of the hat Steam picked. Unknown restrictions and unsupported recipe families refuse. Inventory ships in 0.2.0 by the owner's decision; implementation/simulator checks are not live or packaged acceptance, and the readiness record keeps those limits. Current operation boundaries and testing are in `docs/audits/2026-09-27-inventory-usability/`.

- **Core owns disk, the crate owns network, the UI owns drafts.** `execs-core` has no networking; `*_fetch.rs` / `gamebanana.rs` download through `net.rs` (one client, `execs/<version> (+https://github.com/rndaom/execs)` user agent, size caps, pinned URLs, sha256 where the source publishes one). Commands in `src-tauri/src/commands/*` are thin: `blocking` / `with_root` / `with_profile` run work off the main thread; writes take the `WriteGate` mutex.
- Native fetches use the owned libcurl client in `net.rs`: every approved HTTPS hop resolves and rejects non-global addresses, then binds direct connections and proxy tunnels to a vetted numeric address while retaining the URL hostname for TLS and HTTP. Redirects are checked separately; the shared client reuses a connection only for the same host, vetted address and proxy settings.
- Configured proxy hosts retain their normal DNS resolution. The scoped D8 binding review passed Windows/Linux product proxy fixtures and hosted native/package checks. Debian packages declare OpenSSL/zlib runtime dependencies; the AppImage bundles OpenSSL and uses host zlib under AppImage's base-library policy. Live CDN redirects and installed-candidate upgrades remain release checks.
- **Errors** are `{ code, message }` (`error.rs`); the frontend's single `call<T>()` in `lib/bridge.ts` turns them into `BridgeError`. Every command has a preview twin in `lib/preview-bridge.ts` (the `Api` type is derived from `bridge.ts`, so a new command cannot be forgotten there).
- **Record contracts:** `execs-core` `contracts.rs` serializes fully populated `ProfileDetail` (with HUD, crosshair, viewmodel recipe, hitsound and every mod source) and `ProfileLibrary` into `apps/desktop/src/lib/contracts/*.gen.json`; `lib/contracts.test.ts` checks those fixtures and the preview twins against the bridge types with compiler-checked key lists in both directions. Changing a serialized record means updating the TS type and regenerating with `EXECS_UPDATE_CONTRACTS=1 cargo test -p execs-core --lib contracts`.
- **Pane logic lives in `lib/*-ui.ts` with unit tests**; components stay thin. Drafts use `useSeededDraft` keyed by profile id so a switch never leaks a draft into another profile.
- **Activity log:** `execs-core` `activity_log.rs` appends one line per command failure (every `CommandError::new`), finished profile, mod, HUD and pack operation, absorb that changed something, and network failure (with its full URL) to `<data dir>/logs/activity.log` (256 KB, one rotated generation). Lines carry no file contents and mask password/token values; writing is best effort. Copy diagnostics adds the Health summary and the last 30 lines.
- **Crash hardening:** no `panic = "abort"`; panics log to `<data dir>/logs/panic.log`; the lock poller wraps each tick in `catch_unwind`; heavy work never runs on the main thread.
- **Data dir:** Windows `%AppData%\execs`, Linux `$XDG_DATA_HOME/execs` or `~/.local/share/execs` (`settings.json`, `profiles/`, caches per feature, `preloader/originals` snapshots, `logs/`). Not Tauri's app-data dir.
- App settings Health (`execs-core` `health.rs`, `get_install_health`) is read-only: confirmed root, active cfg layer, pending switch/profile/Casual journals, per-profile missing library bytes (stat only) and uncached direct-author Casual downloads, the picked Steam account's local Cloud `config.cfg`, HUD catalog cache age and legacy library presence. Unreadable evidence is unknown; a local Cloud copy is never described as a confirmed upload; no Steam verification or fetch starts.

## Integrity rules

- The file-safe surface is `tf/custom/`, `tf/cfg/overrides/` (or the vanilla `tf/cfg` user files when mastercomfig is absent), and TF2's Steam Cloud `config.cfg` copy. Nothing else is written, with one exception below.
- **Never** write `tf/cfg/user/`, `tf/steam.inf`, or anything while the game runs. Never store `-autoconfig`, `-default`, `-dxlevel` or `+quit` as TF2 arguments on a profile; a Steam wrapper through `%command%` (such as `gamemoderun`, `mangohud`, `gamescope --` or environment variables) is kept exactly as written and only the arguments after it are checked. Never write `localconfig.vdf` while Steam runs.
- **Write lock:** exact process names `tf_win64.exe` and `tf.exe` (Windows), `tf_linux64`, `tf_win64.exe` or `tf.exe` under Proton (Linux). `refuse_if_running()` guards every live-surface and library write; app-data settings writes stay allowed. Pending launches can be released while Steam remains open after two absent-TF2 samples; a ten-minute timeout uses the original durable marker time across restart. Releasing the wait does not cancel Steam's queued launch, and a later TF2 process still engages the normal write lock.
- **Preloader exception (Mods pane):** `gameinfo.txt` gets only the reversible `type multiplayer_only` ↔ `//type` toggle, pristine copy backed up first; `particles/*.pcf` DATA is patched in place, size-preserving, inside the sibling `tf2_misc_*.vpk` archives. **The `_dir.vpk` is never written, not even a CRC**: the directory carries Valve's tree checksum and sv_pure validates against its stock CRCs, so a rewritten CRC makes pure servers reject the whole archive (magenta everything). Every patched entry is snapshotted first; Restore stock files puts every byte back.
- Every write to a file that matters goes through `hash::write_atomic` (`<file>.execs-part` then rename). Absorb repairs a write that was cut off mid-copy (see Profiles).

## Profiles

- A profile = user cfg layer + `tf/cfg/config.cfg` + all of `tf/custom/` + launch options + records for HUD, crosshair, viewmodel, hitsounds and mods. Library at `profiles/<uuid>/` with `manifest.json` (per-file sha256), exclusive trees, `mastercomfig-base.vpk` shared by hash. Export/import is a zip.
- There is no community hub and no profile uploads. Sharing is the export zip, sent however the player wants.
- Import also accepts creator ZIPs with `cfg/` and/or `custom/`, at the root or inside wrappers (including `tf/`). One cfg tree and multiple custom trees can be combined; destination collisions still fail. Missing `config.cfg` is seeded from the confirmed install's `config_default.cfg`, and legacy `<pack>/UI/{hit,kill}sound.wav` files move to `execs-hitsounds/sound/ui/`; review notes disclose both. Optional variants outside the cfg/custom layout and launch-option instructions stay in the source ZIP. A review names the new profile, counts imported/skipped files, and flags cfg commands before explicit trust; approved cfg bytes (including flagged saved server credentials) stay unchanged. Archive/path/parser limits always apply, native exports retain strict validation, and credential-bearing bytes are disclosed before a player shares an export. Import never activates the new profile or merges in the current setup; its result stays visible until dismissed or switched.
- Source rejects loose outer custom folders named `materials`, `maps`, `resource`, `scripts`, `sound`, or `models` without case sensitivity. Mod/HUD imports allocate safe outer names; native profiles retain their original paths until the user reviews Repair folder names. Repairs preserve payload bytes, use the profile transaction and excluded HUD backup container, and refuse active live drift or selected particle sources that would lose their mod identity. A same-named `.vpk` remains valid.
- Folder repairs remap profile-owned saved particle selections together with their mod records, including inactive profiles. A profile that still owns installed particle sources must restore or clear that projection before repair; other profiles' saved selections and shared projection stay unchanged.
- Profile export scans cfg members inside Source-signature VPKs through the bounded parser and binds inspection and copying to the manifest hash. Before export, a revision-bound review counts the included custom packs, lists up to 50 pack roots with file counts, flags Crosshair scripts and Viewmodels VPKs, and names possible saved-credential locations. It does not remove or license any bytes in the ZIP. Credentials are preserved with the player's own cfg bytes; malformed signed VPKs, parser limits and source changes refuse export without replacing the destination. Legacy files without the four-byte Source signature stay opaque; they still require exact hashes and normal archive limits.
- **Switch is exact replace, not merge.** Sources are validated before the Remove step, files are written atomically, the active id flips last; a failure after Remove clears the active id and the UI says re-apply. Previous exclusive files are removed only when the live hash still matches.
- Switching away from a profile with still-installed Keep packs requires capturing them into that profile or removing them first; no target replacement or unowned pack carryover occurs. Deleting an active profile with Keep installed leaves a durable handoff marker; Save current as… captures the retained setup before another profile can switch in.
- **Absorb** runs on boot and after TF2 quits: owned-file and `config.cfg` drift goes into the active profile automatically (Cloud copy dual-written). The named profile's new and missing packs receive individual Add, Remove from profile, Restore or Keep choices with explicit switching consequences. A full-hash review fingerprint binds the manifest, complete inventory and saved bytes; all choices commit together or refuse as stale. Keep is remembered in `ignored_packs`. Never silently roll the live folder back.
- Automatic absorb uses bounded disposable length/time/identity hints for unchanged ordinary custom payloads only. Cfgs, reviews, switches and mutations retain complete hash checks. An unreadable or over-budget inventory never implies deletion or a partial profile; errors name the responsible path. Valve's root cfgs, including `server_*.cfg`, `replay_example.cfg` and game-owned `sixense_bindings.cfg`, are excluded from ownership, historical projection and deletion. Older exports verify their original hashes before skipping these protected entries with review disclosure.
- Custom inventory fails on unreadable files or directories instead of inferring deletion. Absorb commits additions and removals together, matches full manifest paths without case sensitivity on Windows, and refuses live paths that collide under portable profile identity on any platform.
- Absorb reconciles touched mod records and file/byte totals in the same library transaction as accepted inventory changes. Confirmed HUD removal clears its selected record; Keep, Restore, unreadable inventory and inactive saved packs do not imply deletion. Managed sound/viewmodel packs retain interrupted-write self-repair.
- Accepted ordinary external packs receive stable `External` Mod records while retaining their original folder or VPK names, including through export/import. Accepted drift to managed crosshair, viewmodel or hitsound payloads marks the saved source unverified; a change to crosshair CVars in the Gameplay cfg does the same. Unrelated Gameplay values do not change crosshair provenance.
- **Junk is never a pack:** `*.execs-part`, and Steam's own `tf/custom/readme.txt` and `workshop/`, are ignored everywhere. **Self-heal:** before classifying, absorb rewrites any manifest file missing from the live tree when its `.execs-part` sibling exists or the pack is app-owned (`execs-*`), deletes stray part files, and drops those keys from the ignore list (field incident: the dev app restarted mid-switch and left a half-written viewmodel pack).
- `tf/custom/execs-preloader.vpk` stays outside ordinary pack inventory (`GLOBAL_CUSTOM_FILES` in `surface.rs`), but its addon/particle selections belong to the profile. Switch validates and replaces this shared projection, restoring old particle patches before publishing the target id. A preloader journal inside a pending switch rolls back before that switch retries. Legacy global selections migrate only to previously recorded preload profiles; imported profiles default to empty selections. Profile exports carry these selections.
- Profile ZIP imports use the themed review modal and real read/review/save progress. The backend retains the source path and exact-byte review behind a single-use token; confirmation rechecks the root, write lock and ZIP hash. Cancelling a review writes no profile.
- The switch progress panel shows only real steps (game closed → pack current → remove → write → Cloud → done), paced to a minimum display time; never invented steps or percentages.
- Restore points (`execs-core` `restore_points.rs`) are verified native profile exports in `<data dir>/restore-points/<token>.zip` with `<token>.json` metadata (profile id and name, optional label, strictly increasing millisecond time, size) written after the ZIP; a ZIP without metadata is unlisted and cleaned by the next save. Saving is a library read under the library-read gate and allowed while TF2 runs; unabsorbed live edits are not included. Retention (`retention.json`, 1–20, default 5, UI offers 3/5/10) removes the oldest per profile only when saving or changing the bound; points of deleted profiles stay listed until removed. Compare reads the ZIP manifest and managed cfgs without extraction; Restore imports through the native import path under a new name as an inactive profile, scanning cfg bytes with the same trusted mode export used (a shared ZIP from someone else keeps the stricter scan) (write lock, recovery refusal, stock-built rebuild checks). Recovery journals are separate and never pruned here. There are no automatic restore points yet.
- Rename changes only a profile's display name, inline from its action menu, through the ordinary journaled profile transaction (manifest and index together). The UUID, files, shared blobs, records and active tracking are unchanged and nothing in TF2 is written. Names follow creation rules (trimmed, 1–80 characters, duplicates allowed) plus the import rule against control characters; the library write lock applies.
- Duplicate copies a saved profile into a new inactive profile with a fresh UUID, asking only for a name (default "<name> copy"). It reads library bytes only: exclusive files are copied, shared blobs are referenced, each copy must match the source manifest hash, and live drift is never included. HUD/crosshair/viewmodel/sound/mod records, launch options, ignored packs and preload selections come along; Steam launch-option projection starts pending. Creation stages everything and publishes the index last, so a failure leaves no partial profile. Profiles that need folder repair cannot be duplicated.
- Copy to profiles… in Binds, Gameplay and Sounds (`execs-core` `settings_copy.rs`) copies the active profile's saved settings into chosen inactive profiles, each in its own library transaction; TF2's folder is untouched. Binds replace the target's `execs_binds.cfg`; Gameplay and Sounds replace only their own scope lines in `execs_gameplay.cfg` (never the cheat-only `r_drawtracers`), and Sounds also copy the hit/kill WAVs and record. Each target keeps its own cfg layer and gets the managed autoexec exec line. A review lists every other profile, preselects those that would change, and the action waits for unsaved changes, TF2 and other writes.
- Compare with current… (`execs-core` `profile_compare.rs`, `compare_profile_switch`) reads the active and target library manifests plus their managed Gameplay/Binds cfg bytes: HUD, hit/kill sound names, redacted launch options, top-level custom packs and `tf/cfg` files by combined hash, config.cfg (with its local Cloud copy noted separately from Steam's upload), managed values and Casual choices, and whether the target switch preflight would refuse. Credential commands are never returned. Switch from the dialog re-reads the comparison and shows it again if either manifest revision changed; the switch itself keeps every existing guard. One-click switching from the list is unchanged.
- Profile deletion is an explicit library operation with Export first and Cancel available. Deleting the active profile requires either switching to another profile first or keeping the installed setup and clearing its tracking; deleting the last profile keeps the installed setup. The index is the deletion commit point, a bounded journal makes interrupted cleanup recoverable, and deletion never removes TF2 files. Draft and write-lock guards remain mandatory.

## First run

Find TF2 through Steam library folders (registry, `libraryfolders.vdf`, `~/.steam`, Flatpak, Snap), accept only a root whose `tf/steam.inf` says app 440, always offer Browse, remember the root only after Confirm. Existing customization → **Save current as…** only. Unused install → the setup wizard (name, preset, official addons). Create new profile reuses the wizard (**Create** leaves the new profile inactive and TF2 untouched; **Create and switch** also switches) with **Start from: Current setup** (copies the active live `config.cfg` verbatim under the write gate, including edits since the last absorb, so no tutorial pop-ups) or **Fresh TF2** (Valve's `config_default.cfg`). No silent write before the path is confirmed.

A remembered folder that no longer holds TF2 (a disconnected drive, a changed drive letter, a moved install) is named on the finder with Retry instead of looking like a first run. When the confirmed install differs from the library's recorded folder and that folder no longer holds TF2, **Move profiles here** (`profile_move.rs`) rewrites only the recorded folder: manifests first, index last, so an interrupted move is simply offered again. The active profile stays active only when the new folder holds every file it installs (config.cfg need only exist); otherwise no profile is active and the old one is recorded as interrupted so the next switch removes its matching files instead of merging. The move refuses while TF2 runs, while the old folder still holds TF2 (Change install selects it instead), or while a profile, deletion or preloader recovery record from the old folder is pending. Profile files, blobs and TF2 are never written by the move.

## Panes

- **Backdrop** — every page (the ready shell's workspace, and first-run and library screens without the sidebar, where it stays anchored while the page scrolls) sits over a quiet dot field (`components/DotBackdrop.tsx`, `lib/dot-field.ts`, `lib/backdrop-knockout.ts`): the TF2 emblem as a halftone of execs' orange dots, anchored in the bottom-right corner and partly cropped by it, strongest at the corner and dissolving toward the page's text, over a faint neutral grid. Every dot that would touch a visible line of text or a control is switched off, so nothing is read over dots; a page-coloured layer with one pixel per dot, scaled up without smoothing so it never shades the page, follows the text through scrolling, content changes and transitions. The pointer stirs the dots: those within reach slide aside and a little along its motion, then spring back once it rests or leaves. They brighten only slightly and keep their colour; there is no trail, glow or lens. The field is painted once per size and only the stirred patch is redrawn; frames run only while dots or text move (capped near 120 per second), and reduced motion keeps the still image. The installed app reopens the pane it last showed (Comfig the first time; browser previews use their fixture pane) and restores the main window's size, position and maximized state from `settings.json` (`window`, additive), unless the saved position is no longer on a connected monitor.
- Dense panes fold their advanced depth by default, with the fold's summary saying what is inside (Comfig's "Fine-tune modules" names how many modules differ from the preset; class cfgs and launch options that can change a pane's values sit in a fold below its controls). Folds remember their state per profile; nothing is removed.
- **Comfig** — offers mastercomfig's current Ultra, High, Medium, Low and Custom presets, modules and official addons through our UI. Removed Medium High and Medium Low and delisted Destitute remain readable on existing profiles but are not offered for new selection; no legacy choice changes automatically. VPKs come from mastercomfig's GitHub releases; writes `tf/cfg/overrides/{setup_hook,modules}.cfg`. Extras and the preset guide open in an in-app `WebviewWindow` with no IPC. Credit comfig.app; never brand as official.
- **Binds** — click-to-record for the usual actions; writes `execs_binds.cfg`. Standalone, uncommented binds for known actions in that file belong to the pane; sync and recording retain every other line byte-for-byte. Actions are grouped by player task under an All view with category tabs and a search that matches action names, player words and bound keys. Each action shows its inspected startup keys as readable key caps; the CFG line that last assigned a key is in its tooltip and accessible name, and every key offers remove. Voice-command actions use `voicemenu <menu> <item>` from the pinned dump. Recording adds a key without silently removing other keys; a key already running a different command requires review before its new assignment. Remove leaves the key running nothing: it deletes the pane's own line when nothing earlier binds the key, otherwise it writes one standalone `unbind <key>` (also pane-owned) so an inherited `config.cfg` binding never comes back; a key a later startup cfg binds again is explained and left unchanged. Recording the key again replaces that unbind, and the after-game sync drops it only when TF2 bound the key again. Class, launch and in-game commands may change the runtime result. Autoexec exec lines are addressed from `tf/cfg` (`exec overrides/execs_binds`): the engine resolves `exec` per search path, so a bare stem inside `overrides/` silently fails (field bug). No alias studio, no generated `unbindall`.
- **Gameplay** — world FOV, first-person tracers (never the cheat-only `r_drawtracers`), mouse sensitivity, weapon and combat-feedback comfort toggles; writes `execs_gameplay.cfg`, and links to Viewmodels for viewmodel settings. Transparent viewmodels is an addon VPK toggle, never a cvar.
- Mouse `sensitivity` and `zoom_sensitivity_ratio` are exact decimal fields owned by the Gameplay scope (native `managed_cfg` and the frontend scope agree); input accepts plain positive decimals up to 1000 because the pinned dump documents no range, and an invalid entry is shown with a reason but never saved. Because the managed cfg runs after `config.cfg`, a completed absorb that saw `config.cfg` drift rewrites only the managed lines when TF2's options changed them; the sync never adds lines the managed file did not set. Raw input and acceleration stay with mastercomfig's Flat mouse addon, and no recommended sensitivity is offered.
- Gameplay's Weapons group holds auto reload, fast switch and Medigun auto-heal (`tf_medigun_autoheal`); Combat feedback holds damage numbers, combined damage numbers and healing numbers (`hud_combattext`, `_batching`, `_healing`). All are archived client cvars with no sv_cheats or server requirement; values seed from the effective cfg and TF2's defaults apply only when absent. Colors and the batching window are not offered. The same after-game sync covers these toggles, auto reload and fast switch because TF2's Advanced options write them to `config.cfg`; it accepts only values those options would write.
- **HUD** — hud-db catalog (paginated, sorted by name / tf2huds.dev listing activity / downloads / views from exact matched statistics, cached a day), one HUD per profile, install kinds by host (GitHub codeload zip, Dropbox `dl=1`, GameBanana download page, teamfortress.tv thread scrape, or link out), import picker offers ZIP/7z/RAR/folder, and Dropbox, teamfortress.tv and single-file GameBanana HUD downloads accept the same three archive formats through the shared bounded reader, TF2HUD.Editor schemas consumed as data (parser strips `//` comments, options may lack `Name`). Listing activity is not a HUD release date; missing statistics never enter metric rankings. Imgur albums open in the browser; GitHub `showcase.md` albums load in-app.

## Updates and release

Playbook: `docs/RELEASE.md`. Users install published GitHub Releases only. `main`, Linear, and draft / `workflow_dispatch` builds are private development. No nightlies, no public prereleases, no "try this build."

The 0.2.0 release scope and qualification record live in [release-0.2.0-readiness.md](release-0.2.0-readiness.md). Inventory shipped in v0.2.0 by the owner's September 27, 2026 decision. Design concepts and qualification evidence live in [the overhaul record](design/2026-09-22-overhaul/README.md).

In-app updater (Tauri updater plugin) against `https://github.com/rndaom/execs/releases/latest/download/latest.json`; check on launch and from App settings (or the first-run footer), install only on click, no telemetry. Windows NSIS per-user with `installMode: passive`, static MSVC CRT, `longPathAware` manifest; Linux AppImage (GStreamer bundled, self-updates) and `.deb` (first install only; the publish job strips it from `latest.json`). Signing: updater minisign key in CI secrets; installers are not Authenticode-signed; on September 26, 2026 the owner decided 0.2.0 ships unsigned and moved Authenticode (RND-191) out of the release. App settings has Report a bug (issue forms) and Copy diagnostics (`get_diagnostics`); first-run screens link there from their footer.

Update offers and native installation identity follow the newest completed successful check; a successful no-update result clears the offer, a failed check preserves the last successful offer, and obsolete checks cannot publish an identity after releasing their resource. Durable maintenance preflight failures show a copyable native error before the webview, background poller or command writers start; the version and state location remain visible and recovery markers are never cleared by that error path.

Versioning is `0.Y.Z` until a yearly review promotes 1.0.0. Patch (`0.Y.Z+1`) releases are bugfix-led, not bugfix-only: fixes are the default scope, but when the owner explicitly assigns a bounded, non-breaking feature or polish item to a named patch, that instruction defines the update. Record the exception in the milestone and keep older profiles and exports readable; additive internal recovery metadata remains allowed. Patch releases ship anytime — same day for install, updater, data-loss, or write-lock breaks. Minor (`0.Y+1.0`) is the monthly train (first Thursday, skip if empty): at most three planned user-visible features, or one large feature that is the whole release; profile and write-surface changes stay additive. Breaking changes (new write targets, unreadable profile/manifest, updater URL/key, dropped OS) need a minor and a `Breaking:` changelog line. Never put a breaking change in a patch.

When the owner explicitly requests a hotfix retaining the public product version, use a positive numeric build revision `X.Y.Z+N` (`1..65535`) in all four version files, the changelog heading, signed updater feed and a new immutable `vX.Y.Z+N` tag. Ordinary UI shows `X.Y.Z`, with `Hotfix N` where useful; diagnostics and update/release-note identities retain the full revision. The pinned Tauri updater compares Rust semver total ordering, including numeric build metadata; release probes verify old-to-hotfix discovery and no repeat offer after installation. Do not overwrite a published tag or its assets. Publish the verified hotfix as the latest stable release on the existing updater URL and signing key.

Release = write `CHANGELOG.md` `## [X.Y.Z]` (including `+N` for an explicitly requested hotfix), set `version` in `apps/desktop/package.json`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`, and `src-tauri/core/Cargo.toml`, push the matching `v` tag. The workflow guards the version, builds both platforms into a draft, sets the release body from the changelog (fails if that section is missing or empty), verifies both `latest.json` entries, then publishes.

Private `workflow_dispatch` candidates require the matching `vX.Y.Z` input. Candidate and tag runs for that product version share one concurrency lock because both mutate the same draft. Installer smoke derives the immediately previous public version from ordered changelog history and tests that exact updater path; it is never hard-coded to an older release.

Release verification accepts GitHub's temporary `untagged-...` draft browser slug only when it matches that draft's `html_url` and the feed references its stable API asset URL. The exact `tag_name`, revision and signatures remain mandatory. Previous-installer downloads select actual public asset names, including either literal or normalized numeric build suffixes.

GitHub Issues and Discussions are the public inbox. Linear execs is the backlog. A public thread that becomes work gets a Linear issue labeled `from-github` (and `compat` when it touches profiles, the data dir, the write surface, or the updater). Do not keep a second backlog on GitHub. Every user-facing change adds its `[Unreleased]` changelog line in the same commit.

## Design system

Theme tokens live only in `apps/desktop/src/index.css` `@theme`: bg `#100F0E` → panel `#1C1A18` → panel-raised `#292622`, warm off-white ink `#F2EFEB`, secondary ink `#CAC5BF`, faint ink `#ADA59E`, TF2 orange accent `#D98449`. Orange marks primary actions, selection, navigation and necessary highlights; orange/red warnings and green success colors carry actual state. No yellow warning treatment. Use Inter and Phosphor icons, six type steps (`.t-pane`, `.t-section`, `.t-row`, body, `.t-meta`, `.eyebrow`), restrained 4–6px corners, hairlines and compact controls. Flat sections organize settings; actual previews, workspaces, overlays and selectable options may have surfaces. Selected options use a ring, wash and dot, never a decorative checkmark. No `<select>` where a `Segmented` control or a picture grid works; a remaining long choice list keeps the native `<select>` inside `.select-field`. Every chooser, menu button, fold and select uses `components/ui/Caret` (12 px bold, faint ink; menu carets flip while open, fold carets turn down), never the browser's `<details>` marker or platform select arrow. More-actions buttons use one horizontal ⋯. Lists of things with actions (Files, Inventory items, profile rows) also open those actions on right-click through the shared `ContextMenu`. Use switches rather than native checkbox visuals. Files keeps its bounded, fixed-width source editor exception. Task-specific pane composition is required: settings may pair one decision with a 360px preview, while catalogs, sound slots and Files retain suitable workspaces.

The shared shell uses a stable header, 180px sidebar, separate global App settings and per-pane scroll memory.

- The orange dot is execs' signature and means "a change": it is the wordmark's dot, which breathes while a change saves and pops once when one lands (quiet autosaves included), and it marks a sidebar pane whose changes have not reached the profile yet (a waiting settings draft or unsaved Files edit). Selected option tiles keep their dot. The active sidebar item is a flat highlight that glides between items, not a dot. Tab underlines and segmented choices also glide; folds open smoothly where the engine supports it.
- The loading indicator is a flat redraw of the TF2 emblem stepping through quarter turns (`components/ui/Spinner.tsx`); the owner chose this on September 26, 2026 knowing the emblem is Valve's mark. Whole-surface waits use `LoadingState`. TF2 class emblems (`materials/hud/leaderboard_class_*.vtf`) are decoded read-only from the player's own `tf2_textures_dir.vpk` by `get_class_icons` and flattened into single-colour masks; the preview and any unreadable emblem fall back to text. No other Valve artwork is vendored. Profile/install changes reset profile-owned pane positions; account Inventory and App settings retain their separate context. Hidden panes release captures, overlays and playback while keeping session drafts. Motion is 150ms color/opacity and 220ms local movement, with no perpetual decoration beyond a spinner during real work; `prefers-reduced-motion` or app Reduce removes transitions. On the owner's September 27, 2026 request, loading is choreographed: index.html draws the page colour and the spinning emblem before any script runs; `components/BootSplash.tsx` adds the wordmark and the real read startup is waiting for (install lookup, profiles, first-run check, the opening pane) and holds at least 1.1 s, never more than 10 s, while the app beneath stays inert; it then lifts off and its wordmark travels onto the first screen's own wordmark. Each new screen enters in order (header, sidebar, then the pane's sections, or an onboarding frame top to bottom; `lib/entrance.ts`), pane switches and a profile's finished settings read stagger the pane's sections, and whole-surface waits fade in after a short delay so quick reads never flash a spinner. A confirmed install stays on the finder about 1.3 s showing Install confirmed and the filled setup steps while the next screen's reads finish. Holds exist only to show real results; reduced motion and tests skip them. Copy uses sentence case and buttons that say what happens. Show helper text only when it explains behavior, a constraint or a consequence that the control itself does not make clear; remove decorative ledes and redundant subtext. Verify layouts at 1200×800 and 960×640 with genuine source imagery; generated concept boards never supply shipped preview assets.

Promo media: `tools/promo` captures the release-looking browser preview (development-only surfaces compiled out, HUD and mod art hosts blocked) with its own fixture data, and composes the promo video in Remotion around the orange dot, cut to an original soundtrack synthesized by `music/compose.mjs` from a shared 120 BPM timeline. The README shows it as a silent 30 fps GIF (`docs/media/promo.gif`, built by `gif.mjs` from lossless frames with one palette per scene); the MP4 with sound is for other platforms and is not kept in the repository. On September 27, 2026 the owner allowed TF2's class emblems and a real backpack in promo media: class emblems are decoded from a local install, and the Inventory scenes use the owner's local Inventory art cache (Valve's item images and descriptions) in the app's own simulator with the Steam persona, avatar, account ID and "Crafted by" lines left out. Both reach only rendered frames and screenshots, never the repository as separate files.

Pending-change dialogs wrap complete cfg paths. Their Open pane actions move keyboard focus to the visible destination heading after dialog cleanup; ordinary navigation and Cancel retain their own focus behavior. Close decisions consult the live settings-write guard before proceeding, including writes that start before React renders the busy state.

The main window enables native page zoom with Ctrl + Plus / Minus and Ctrl + 0. Linux uses Tauri's zoom handler and the main-window-only webview zoom capability. Enlarged layouts retain keyboard access; browser viewport reflow alone does not prove native zoom behavior.

## Platform constraints

- On Windows, launching the dev executable directly from packaged Codex can inherit its MSIX AppData virtualization and mix real profiles with `OpenAI.Codex_*/LocalCache/Roaming/execs` copies. Launch through the existing Explorer desktop's `Document.Application.ShellExecute` instead; confirm `GetPackageFullName` returns `APPMODEL_ERROR_NO_PACKAGE` (15700). Keep profile containment checks intact and do not merge or delete either library to work around this launch-context problem.
- Windows atomic file replacements and HUD backup moves pass absolute verbatim paths to `MoveFileExW`; `longPathAware` alone does not lift MAX_PATH when the system long-path policy is disabled. Preserve containment checks and resolve only endpoint parents so absent destinations and leaf rename semantics remain supported.

- Linux AppImages use the host Wayland libraries with the host EGL drivers. The before-bundle hook installs a project-local output plugin wrapper that removes only bundled Wayland libraries after deployment and before packaging/signing; keep the artifact check in installer smoke.

- Viewmodel compiler launches use Windows `CREATE_NO_WINDOW`; redirecting stdout/stderr alone still flashes a console for each class.
- Release builds enforce `tauri.conf.json`'s CSP; `tauri dev` and the browser preview do not (`devCsp` is null). Tauri adds a nonce to every inline `<style>` in `index.html`, and a nonce makes browsers ignore `'unsafe-inline'`, which blocks the styles CodeMirror injects at runtime and leaves the Files editor unstyled. Keep startup styles in the linked `src/boot.css`; `lib/boot-ui.test.ts` refuses an inline `<style>`.

- Launching the real game for a test must not pass video flags (`-w`, `-h`, `-windowed`, `-noborder`, `-fullscreen`, `-dxlevel`): Source persists them into `HKCU\Software\Valve\Source\tf\Settings`. `-condebug` is fine; `-console` persists `con_enable`.
- An isolated `-game` directory does not isolate Steam Cloud: retail TF2 can still overwrite the account's `440/remote/cfg/config.cfg`. Do not use it as a player-state sandbox. Keep native verification in disposable core fixtures unless Cloud isolation is independently established; any approved real-game test must retain exact original bytes as well as hashes before launch.
- `C_OP_RenderSprites::RenderUnsorted … unimplemented sprite renderer` console floods mean a particle system whose material failed to load, not a PCF bug.
- comfig.app's CDN challenges empty or bare-library user agents; our UA string is enough.
- GameBanana's `Generic_LatestAdded` sort does not exist (`Generic_Newest` does); listings carry no download counts.
- Linux clippy flags imports used only by `#[cfg(windows)]` tests: import inside the test fn.
- User-facing changes add a `CHANGELOG.md` `[Unreleased]` line in the same commit.

## Compatibility and retained behavior

These requirements originated in earlier releases and continue to constrain compatible changes.

### 0.1.2 draft integrity

- Visited settings panes retain drafts until saved or explicitly discarded; hidden panes release keyboard capture, modals and audition playback. Pending autosaves pause profile changes and game launch. Files drafts stay in session memory keyed by profile and path.
- Failed or refused autosaves remain pending, retry after TF2 unlocks, and preserve edits made during an in-flight save. Settings identity and cfg seeds publish only after a complete read; incomplete reads keep writes blocked until retry succeeds.
- Managed cfg and autoexec updates execute together under the native write gate. Gameplay, crosshair and sound saves merge only their own commands into current bytes so deferred edits from different panes cannot overwrite each other.

### 0.1.3 bind and integrity fixes

- Published 0.1.3 is based on the 0.1.2 tag through its maintenance branch; creator-profile and profile-scoped-preloader schema work remains on the minor track. Future patches start from the latest public maintenance baseline.
- Binds records DOM right/middle buttons as Source `mouse2`/`mouse3`, retains profile-scoped drafts while TF2 runs, and synchronizes tracked removals from a complete post-absorb `config.cfg` read.
- Absorb rechecks the live process before each restore, repair and config/Cloud mutation. Catalog matching keeps an imported HUD's local tree editable, and profile ZIPs apply the bounded small-entry compression exception used by HUD archives.

- Settings seeds reconcile before autosave effects run, so a reload that lifts a write lock cannot save the previous seed back over newly loaded settings. Busy transitions only defer a pending absorb; they do not create new external-change events. Pack prompts belong to the profile and complete snapshot that produced them.
- A leading dash does not disable a HUD in Source. Replaced HUDs with changed or unowned files are preserved below `tf/custom/execs-hud-backups/<token>/<original-folder>/`, outside mounted HUD content roots and excluded from profile inventory. Exact profile-owned trees use existing verified library history without an extra live copy. Legacy profiles retain extra HUD files in the library while only their selected HUD projects live.
- In 0.1.3, default-library preloader choices remain global. Profile-sourced particle patches are removed before a profile switch; stale source references reconcile under the write gate instead of becoming hidden, unremovable picks in another profile.

### 0.1.4 crosshair update

- Crosshair has one In-game / Custom mode choice and one color owner. Color and display size autosave; custom asset changes use Build pack. A mode change that changes mounted files requires its explicit action under the write gate.
- Inactive custom assets remain under `tf/custom/execs-crosshairs/inactive/`, where their `materials` and `scripts` trees are outside Source's mounted content roots. Deactivation and reactivation use the existing recoverable profile transaction, preserving designs, library assets and per-weapon assignments in exports. Old crosshair records default to active; optional scale and stock-selection metadata preserve inactive settings.
- Custom display size uses `cl_crosshair_scale` (16–64), with original weapon-script width/height retained. Valve's HUD reader uses width/height for texture coordinates as well as display dimensions, so changing only those fields crops the image. Both stock and weapon-defined sprites apply the scale cvar; previews retain intrinsic dimensions against a labeled 1280×720 neutral, code-native reference scene.
- The designer retains old single-design parameters and accepts a named design map in the existing opaque design field. Textures remain untinted; the shared RGB cvars own color. The pending-save banner is removed; pending-save transition guards and the Files Save / Discard / Cancel contract remain.

### 0.1.7 Hotfix 2 Files usability

File info is not a separate surface; secondary actions live in file and editor menus. These tools never append unrelated surface cards that scroll the editor out of context.

### 0.1.5 mutation outcomes

- Installed sound auditions read current bytes on each play, invalidate on profile or installed-record changes, and revoke their transient URLs. ### 0.1.5 cfg integrity

- Cfg safety scanning includes dormant files and bind/alias payloads without changing derived settings. Settings evaluate only known startup entry points and invoked exec/alias chains in order; definitions do not execute their payloads, and executed unbind operations remove bindings. A shared command/exec budget bounds both passes; incomplete execution blocks derived settings writes while Files remains available.
- Loose cfg startup and exec resolution uses immediate non-dot `tf/custom/<pack>/cfg` roots in case-insensitive ASCII mount-name order before `tf/cfg`; nested inactive/backup cfg folders do not become mounts. Case-colliding or unsupported mount order refuses inference. Derived saves stay blocked when a pack shadows the managed startup or settings files because native saves never rewrite provided packs.
- A legacy manifest with multiple HUD roots and HUD cfg files does not establish which cfg trees project live. Derived settings remain blocked with Save current as… recovery until a complete mounted setup is captured; Files stays available and no frontend HUD projection is guessed.
- Gameplay preserves `viewmodel_fov` throughout Source's 0.1–179.9 range without rounding incoming decimals. The viewmodel slider selects whole numbers once moved; it does not rewrite a fractional value loaded from cfg until that control changes. World FOV uses TF2's effective 75–90 control; lower saved values display 75 with an explanation and remain unchanged until that control is edited.
### 0.1.5 pack and cfg integrity

- HUD option apply stages the whole tree before publishing. Resource edits preserve untouched text spans and BOM/legacy bytes; logical `Resource/*.res` and `Scripts/*.res` include headers must be unambiguous. Folder choices use portable validated moves, and schema expressions resolve from one complete option/default snapshot without executing code.

- A leading dash is part of a custom pack's literal identity. Absorb, Keep, removal and switch cleanup never substitute a dashed/undashed peer. Legacy HUD backup recovery requires a recorded inactive undashed HUD, no live undashed peer and no manifest ownership of the dashed path; coexisting or unknown dashed HUDs keep their normal identities.
- Cfg-layer detection reads the mounted startup autoexec and core cfg through one bounded content check. The supported mastercomfig loader executes `comfig/comfig.cfg` followed by `overrides/autoexec.cfg`; addon names and leftover overrides are not loader evidence. Inventory preserves safe nested user cfgs and overrides in both layers. Managed binds/gameplay writes refuse a live/library loader mismatch until the external change is resolved.
- Cfg inventory handles `user`, `app`, and `overrides` specially only when they are immediate `tf/cfg` children. The same names deeper in a user cfg tree remain literal profile content.
