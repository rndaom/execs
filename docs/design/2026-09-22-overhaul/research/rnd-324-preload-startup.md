# RND-324 — startup investigation and bounded improvement

Status: **partial implementation; issue remains open**. Evidence date: 2026-09-22. This is not a clean-launch, Casual-compatibility or frame-presentation qualification result.

## What changed

`core/src/viewmodel.rs` still produces the established offline `itemtest` preload. The generated cfg now explains that it opens that map and returns to the menu, advises launch-only use, and logs the hook boundaries without asserting that content cached successfully. It no longer clears console history or calls the server-side `script_execute randommenumusic` after disconnect. The original bounded command-buffer delay remains; it is not labeled an initialization barrier.

The launch-option replacement recognizes quoted filenames and the optional `.cfg` suffix in addition to both managed stems. Replacing or disabling an existing selection therefore removes duplicate managed spellings while preserving unrelated `+exec` commands. This is launch-token normalization, **not a runtime once-only guard**. Re-executing the cfg manually or from another user cfg can still run it again.

Casual setup explicitly discloses the offline-map behavior. The improved cfg is emitted when the managed preload is generated or rewritten through existing operations; this change does not rewrite every saved profile on application startup.

## Primary-source findings

- The preloader author's mechanism documentation explicitly describes offline-map preloading as part of its combined mechanism. Its VGUI caching section concerns retaining texture references through offscreen HUD resources; it does not establish a replacement for all model, animation and particle initialization. No GPL implementation code was copied. [casual-pre-loader mechanism documentation](https://cueki.github.io/casual-pre-loader/how_it_works/)
- Valve's command buffer treats `wait` as a tick delay only when waiting is enabled. It neither observes successful map initialization nor provides an error branch. Adding another wait or an alias loop would not establish the requested bounded once-only startup condition. [Valve command buffer, pinned source](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/src/tier1/commandbuffer.cpp#L194)
- The shared `script_execute` server command refuses work without its script VM. The server script system creates that VM during level initialization and destroys it during level shutdown. Calling it after disconnect is not a reliable menu-music restart. [Valve shared VScript commands](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/src/game/shared/vscript_shared.cpp), [Valve server VM lifecycle](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/src/game/server/vscript_server.cpp#L3712)
- Valve's server interface performs precache work during level initialization. This supports caution about replacing the current map lifecycle with a speculative client command; it is not proof that no alternative implementation is possible in retail TF2. [Valve level initialization](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/src/game/server/gameinterface.cpp#L902)

The public SDK is evidence for command semantics, not a runtime trace of the user's installed TF2 build. The generated concept art and the issue's desired behavior cannot establish an engine capability. Deleting required preloading to make the console quieter would regress the first acceptance criterion. Substituting `map_background`, hiding warnings, or claiming an echo means success would not satisfy the criteria either.

## Verification

- Generated-cfg regression keeps one itemtest invocation and the established preload cvars, preserves console evidence, and rejects recursive exec/alias, console clearing and post-disconnect VScript commands.
- Launch normalization regression covers duplicate bare, quoted and suffixed spellings; unrelated exec preservation; idempotent updates; and both vanilla/comfig layers.
- All 19 viewmodel fixture tests passed in the HUD agent's integrated core run after correcting concurrent HUD manifest normalization (`hud_roots: None` versus `Some([])`). This includes existing import, rollback, live drift, game-running and Steam launch-sync fixtures as well as the new serializer/token regressions. It is not a retail-game launch.

Next engine work requires a verified alternative mechanism or a revised explicit preload workflow, plus native clean/failure/re-entry traces in an independently isolated test setup. Qualification must not set video flags or assume an isolated `-game` directory protects Steam Cloud. The recurring in-game FPS issue is not proven to be caused by this startup hook.

## Follow-up: initialization, re-entry and failure boundaries

The bounded follow-up on 2026-09-22 found **no additional proven cfg-only implementation that meets the exact acceptance**. The offline-workflow question is still unanswered; this investigation does not change the map-free requirement or authorize another write target. No product code, installed game, player data or live process was changed. The earlier command-delay and VScript conclusions are unchanged; the new findings below concern the missing map cfg, actual readiness signals and an existing one-shot mechanism.

Sources were pinned to Valve SDK `b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474`, cueki documentation `2ff08522df250df0bc72153866937ea9e60694e4`, and mastercomfig `d947673e721d686a64a3e7055f38197556a3405b`. The latter is mechanism evidence, not a claim about the mastercomfig version in any player's profile. Only cueki's documentation was read for this follow-up; no GPL implementation was copied.

### New primary-source findings

1. **The map-config request is made by TF2 itself.** `CTFGameRules` constructs an `exec` command from the map name and queues it without a file-existence check. Loading itemtest therefore requests `itemtest.cfg`; changing the name of our launch hook or its ordering does not remove that request. This occurs in the gamerules constructor, before its later post-entity initialization function, so placing cleanup in that map cfg would not itself establish a client-ready boundary. [Valve map-config dispatch](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/src/game/shared/tf/tf_gamerules.cpp#L3364), [later post-entity initialization](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/src/game/shared/tf/tf_gamerules.cpp#L3611).

2. **The SDK distinguishes application initialization, map initialization and an active client.** The client DLL interface exposes `PostInit` separately from per-level pre/post-entity callbacks. The engine client interface distinguishes `IsConnected` from `IsInGame`, with the latter representing a fully active client. These are C++ interfaces; their existence does not make them usable as cfg conditions. The inspected post-entity implementation invokes game systems, and event registration requires a listener object. No supported cfg listener or console-return-value branch was established for those signals. [Valve client lifecycle](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/src/public/cdll_int.h#L584), [client readiness interface](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/src/public/cdll_int.h#L281), [post-entity implementation](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/src/game/client/cdll_client_int.cpp#L1682), [event listener API](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/src/public/igameevents.h#L115).

3. **A one-shot alias is a real mechanism, but not a complete startup solution.** mastercomfig invokes its first-spawn callback and then empties the dispatch alias. Its documented `game_overrides_once_c` extension runs with that flow. Valve's TF client executes class cfgs on the local class-change event. This supports a one-shot action after that particular event, not an action after menu initialization or a fallback when itemtest never reaches it. Using that existing extension would also require preserving the player's callback and covering vanilla profiles. It must not become a delayed preload/disconnect when the player's first class selection is on an online server. [mastercomfig first-spawn documentation](https://github.com/mastercomfig/mastercomfig/blob/d947673e721d686a64a3e7055f38197556a3405b/docs/customization/custom_configs.md#L105), [one-shot dispatch](https://github.com/mastercomfig/mastercomfig/blob/d947673e721d686a64a3e7055f38197556a3405b/config/mastercomfig/cfg/comfig/game_overrides.cfg#L8), [callback initialization](https://github.com/mastercomfig/mastercomfig/blob/d947673e721d686a64a3e7055f38197556a3405b/config/mastercomfig/cfg/comfig/comfig.cfg#L1971), [Valve class-cfg trigger](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/src/game/client/tf/clientmode_tf.cpp#L677).

4. **Public source has a precise scope limit.** Valve describes this repository as game code; the inspected tree contains command-buffer infrastructure but not the retail engine's host startup/`+command` dispatcher implementation. Thus this audit cannot prove the exact ordering of `+exec` against retail menu readiness, map-command completion or failure cleanup. The cueki documentation still requires its startup `+exec` and describes the combined mechanism as using an offline map; it supplies no alternative initialization or failure callback. [Valve SDK scope](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/README.md), [pinned cueki startup instructions](https://github.com/cueki/casual-pre-loader/blob/2ff08522df250df0bc72153866937ea9e60694e4/doc/docs/troubleshooting.md), [pinned mechanism description](https://github.com/cueki/casual-pre-loader/blob/2ff08522df250df0bc72153866937ea9e60694e4/doc/docs/how_it_works.md).

### Candidate disposition

| Candidate | What the evidence supports | Why it is not an approved solution |
| --- | --- | --- |
| Supply `itemtest.cfg` | It addresses the specific filename requested by the game. | It is warning prevention only. In a comfig profile, adding `overrides/itemtest.cfg` alone would not match the game's bare filename. A new root cfg or custom-pack member needs ownership/search-precedence review and must not shadow player content. No such file was added. |
| Empty a private dispatch alias before starting work | A self-disabling alias can prevent subsequent calls through that dispatcher. | A repeatable cfg that defines its own dispatcher before invoking it rearms it on each `exec`. Separately seeding the latch could avoid that, but requires a proven startup initialization path while preserving the standalone supported `+exec`, unrelated aliases and both cfg layers. It still supplies no readiness or failure result. |
| Use map cfg, listenserver cfg or class/first-spawn callback for cleanup | These are real lifecycle-related cfg entry points; mastercomfig documents the latter two. | They have different boundaries, may not run on a failed load, and can run during unrelated sessions. The first-spawn extension is mastercomfig-specific. A callback alone cannot be treated as a bounded watchdog. [mastercomfig hook timing](https://github.com/mastercomfig/mastercomfig/blob/d947673e721d686a64a3e7055f38197556a3405b/docs/customization/custom_configs.md#L11) |
| Bind cleanup to SDK readiness/disconnect events | The native interfaces can distinguish those states. | No existing execs or verified cfg interface exposes them. A plugin, modified game DLL, new command channel or injected listener is a different architecture, outside this task and not proposed. |

There is no justification to replace the preserved workflow with one of these partial candidates merely because its generated cfg looks safer. This is a bounded evidence result, not a proof that TF2 can never support another design.

### Exact blockers and next evidence

- **Product/engine contract:** the original normal-launch criterion excludes an implicit map cycle. Retaining the now-disclosed offline preload needs the owner's scope decision; it does not establish once-only, initialization or cleanup behavior by itself. A map-free replacement still requires evidence across the supported model/animation/material/particle workload.
- **Readiness and once-only boundary:** identify a supported menu-ready entry and a process-lifetime latch that survives duplicate managed invocations and accidental autoexec/map/class references without rearming. For an offline design, distinguish map request, server initialization and client activation. The SDK proves those are different boundaries; it does not expose a verified cfg solution for them.
- **Failure ownership:** establish how the hook observes a refused/failed map and prevents a later class/server event from executing stale cleanup. Any success-side callback needs an independently bounded failure path. An echo after dispatch is not success evidence, and unconditional disconnect does not distinguish the temporary session from a later one.
- **Native qualification:** an independently isolated retail setup must record clean/cold startup, ordinary return to menu, duplicate invocation, disabled waiting, rejected/missing map, and interruption before client activation. Cover vanilla and comfig plus representative selected profile sources. The records must show callback/cleanup counts, retained engine errors, no leftover local server or deferred disconnect, and actual cached content on the target workflow. Failure fixtures must be confined to that isolated setup; no installed Valve file should be removed from the player's installation.
- **Presentation acceptance:** once that functional behavior is established, perform the existing short PresentMon comparison with unchanged exclusive-fullscreen/D3D9Ex settings. No video flags, assumed Cloud isolation or source-only substitute can establish this row.

The next justified action is native qualification design after the workflow decision, or investigation of a specific documented alternative provided by an engine/upstream source. This follow-up changes no acceptance status and performs no engine test.
