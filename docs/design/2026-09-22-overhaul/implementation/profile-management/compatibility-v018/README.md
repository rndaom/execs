# Actual public v0.1.8 export compatibility

Passed on Windows on 2026-09-22: four disposable profiles were created and exported by the **actual core library from public tag `v0.1.8`**, then reviewed, imported and re-exported by the current core. All 32 payload comparisons preserved exact bytes and SHA-256 hashes. The previous active profile and the synthetic TF2 root stayed unchanged.

This adds evidence that the existing tests did not provide. The existing ZIP round-trip tests use the current exporter, and their legacy cases construct compatibility inputs. These retained ZIPs were emitted by the tagged old exporter without changing its source.

## Revisions and execution

- Exporter: `v0.1.8`, commit `85aaf6bc0dd28f43351d4cb5cdb62502737688d5`.
- Importer and re-exporter: commit `542b3dd20f2847fc90a1a4e990584f03830fcc6d`. Its core tree had no uncommitted changes before or after the run.
- Toolchain: `rustc 1.98.1 (48a229cea 2026-09-01)`, `cargo 1.98.1 (797e8a9bc 2026-08-05)`.
- The temporary Cargo harness depended on both versions through separate aliases. It used the public tag's lockfile and built offline; all 96 registry package versions and checksums in the resulting harness lockfile matched that tag's lockfile. Cargo added only the current local `execs-core` dependency.
- Final execution: `cargo run --offline --locked -- <fresh absolute results directory>`, exit code 0.

Observed output:

```text
PASS: actual v0.1.8 exporter -> current reviewed importer -> current re-export; 4 cases; all payload hashes and synthetic live snapshots unchanged.
```

## Cases

Every case includes user cfg bytes, a shared mastercomfig-base fixture VPK, an ordinary mod fixture VPK and its ModRecord, and launch options. The Source VPKs are generated by the tagged core's public VPK writer. HUD cases add real UI-version-3 metadata, resource payloads, a saved HUD record, managed option cfg bytes and an autoexec startup line.

| Case | Payload files | Result |
| --- | ---: | --- |
| [No HUD](no-hud/exported-by-v0.1.8.zip) | 4 | Imported and re-exported unchanged. No HUD ownership review pending. |
| [Single HUD](single-hud/exported-by-v0.1.8.zip) | 8 | Original HUD record, options, cfg and payloads preserved. No ownership review pending. |
| [Multiple HUDs, keep owner](multi-hud-keep-owner/exported-by-v0.1.8.zip) | 10 | Import without a reviewed choice refused with `HudReviewRequired`. Explicitly choosing the old owner preserved both HUD originals and all cfg bytes. |
| [Multiple HUDs, change owner](multi-hud-change-owner/exported-by-v0.1.8.zip) | 10 | Import without a reviewed choice refused. Choosing the other HUD preserved both originals, the original HUD record and every cfg byte; `hudReviewPending` became true for the separate options review before activation. |

The two multiple-HUD cases intentionally use equivalent old exports and differ only in the choice passed to the current import review.

Each import also verified:

- The actual old ZIP uses schema 1 and omits `preloader`, `hudRoots`, `hudSelectedRoot` and `hudReviewPending`.
- The imported preloader selection defaults to empty; no preloader state directory is created.
- The existing active profile id and its manifest bytes do not change; the imported profile remains inactive.
- Every imported path, file count, storage class and payload hash matches the exported source. Ordinary ModRecord data, HUD record data and launch options survive; launch synchronization is correctly pending on the recipient.
- The current re-export contains the same payload bytes, including unselected HUD originals.
- The old exporter does not mutate its source library, and snapshots of every file in the synthetic TF2 root remain identical throughout.

## Retained evidence and reproduction

- [results.json](results.json): per-file before/after hashes, archive hashes, resolved data directories, root snapshots and assertions for all four cases. Its absolute paths identify the original disposable run; the corresponding ZIPs are retained under each named case here.
- [harness/src/main.rs](harness/src/main.rs), [Cargo.toml](harness/Cargo.toml), [Cargo.lock](harness/Cargo.lock): the executed harness and resolved dependency lock.
- Each case folder contains the exact old exporter ZIP, its exported JSON manifest, and the current re-export ZIP.

The standalone JSON evidence is formatted for repository readability; its parsed values are unchanged. The retained ZIP bytes, including their original manifest entries, are unchanged and bound to the hashes above.

To reproduce, extract `apps/desktop/src-tauri/core` and `apps/desktop/src-tauri/Cargo.lock` from the stated public tag into a fresh temporary `tagged-source/` directory. Put the retained harness beside it as `harness/`, update only its `new_core` path to the stated importer checkout, and run the command above with a results directory that does not yet exist. The harness refuses to reuse a previous results directory. `--offline` requires those locked dependencies to be cached already.

## Isolation and limits

The harness changes `APPDATA` and `XDG_DATA_HOME` only inside its own child process, before calling either library. It asserts that **both** versions resolve their execs data directory beneath the current disposable case. Explicit library paths, synthetic TF2 paths and any implicit data/preloader fallback remain under that same temporary area. No parent or system environment setting was changed.

No desktop application, installer, Steam or TF2 was launched. No real installation, player library, Cloud configuration or account was read or written by these flows. The core's normal process-name write-lock checks still run. This is Windows **library-level compatibility evidence for these four cases**, not installer/updater, native GUI, real-game/Cloud, Linux, exhaustive historical-profile, or arbitrary third-party-payload qualification. The pending HUD follow-up is asserted, not activated in this harness. There were no product code changes, commits or pushes for this qualification run.
