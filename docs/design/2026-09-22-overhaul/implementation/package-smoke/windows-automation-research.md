# Hosted Windows package UI route

2026-09-22. Read-only research against `d80fe576f90fc0ca8a4e5c37ea8decb8274c4475`. No installer, driver, app or workflow was run for this note. **A bounded hosted route is feasible to implement; an actual Windows package/UI pass remains unverified.**

The [proposal](development-run-plan.md), [current Linux workflow](../../../../../.github/workflows/development-package-smoke.yml), [development guard](../../../../../scripts/development-package-guard.mjs) and [signed package smoke](../../../../../scripts/smoke-packages.mjs) were inspected. The development guard deliberately refuses Windows today. The signed harness tests updater probes and process survival, so it cannot supply the missing rendered UI evidence.

## Supported route and the elevation trap

Use a standard GitHub-hosted `windows-2022` x64 VM and record its exact image version. GitHub supplies a fresh VM and runs Windows jobs as administrators with UAC disabled. Tauri explicitly documents Windows WebDriver tests on GitHub Actions, with `msedgedriver` as its Windows native driver. This supports a hosted experiment, not an assumption that every native dialog or desktop capture will work. [GitHub runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [Tauri WebDriver CI](https://v2.tauri.app/develop/tests/webdriver/ci/), [driver setup](https://v2.tauri.app/develop/tests/webdriver/manual-setup/).

Microsoft supports attaching Edge WebDriver to an already running WebView2 application: `EdgeOptions.UseWebView = true` and `DebuggerAddress = "127.0.0.1:<port>"`. Match `msedgedriver` to the **WebView2 runtime actually used**, not merely the installed Edge browser. Attach mode gives the harness ownership of the installed executable, child environment and normal-exit receipt. The current [W3C client](../../../../../scripts/linux-native-webdriver.mjs) has reusable click, keyboard and observation methods, but its `start()` is Tauri-launch-specific; it needs a small explicit attachment entrypoint or an external Selenium adapter. [Microsoft WebView2 WebDriver](https://learn.microsoft.com/en-us/microsoft-edge/webview2/how-to/webdriver).

An environment-only launch is unreliable here. Current Microsoft documentation says elevated WebView2 hosts ignore `WEBVIEW2_*` and HKCU overrides, while honoring HKLM policy. It also excludes the SYSTEM account. Record the actual account, session, integrity level and package identity; refuse SYSTEM. [Microsoft elevation rules](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security#for-an-elevated-host-app-use-appropriate-override-flags).

The retired `v0.1.7:scripts/qualification/files/webview2-ci-policy.ps1` already snapshots/restores app-specific HKLM `AdditionalBrowserArguments` and `UserDataFolder` values for `execs.exe` and `com.rndaom.execs`. Reuse that narrow pattern **only inside the disposable hosted job**: owned user-data directory, free loopback debugging port, exact prior value/type restoration in `finally`. Verify the actual browser command line, listening address and user-data path. Do not restore the old whole CDP worker: its fixed port, lexical containment and forced shutdown need replacement with current boundaries. No wildcard policy, security-disable flags, app debug feature or production code change is needed. [Microsoft override definitions](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/webview2-idl?view=webview2-1.0.3537.50#createcorewebview2environmentwithoptions).

## Smallest useful hosted experiment

1. Extend the existing development-only job pattern: same-repository PR/manual execution, `contents: read`, no tags or signing secrets, exact checked-out commit, bounded deadlines and evidence-only artifacts. Refuse existing execs/Steam/TF2 processes, product installation and the production finder's Steam registry locations before starting. Use fresh contained `RUNNER_TEMP` directories, child APPDATA/LOCALAPPDATA/TEMP, explicit WebView2 data and the existing synthetic fixture; environment changes alone do not isolate Steam Cloud.
2. Resolve the previous public version using the existing guarded history/asset logic; it currently resolves to `v0.1.8`. Verify its actual NSIS asset with the existing public Minisign key. Build the ordinary candidate NSIS using only the temporary `bundle.createUpdaterArtifacts=false` override from the proposal. Record package hashes, build inputs and runtime/driver versions.
3. Install the old NSIS with `/S` and last argument `/D=<absolute owned install directory>`, then run its **installed** executable. Handle NSIS argument quoting correctly and verify the resulting path rather than trusting exit zero. Capture executable hash/version, notices and package identity. Attach WebDriver, verify the production origin and expected profile/Files content, then perform a real W3C click and Tab navigation. No preview, application IPC, JavaScript click or injected application state. [NSIS command-line rules](https://nsis.sourceforge.io/Docs/Chapter3.html#3.2.1).
4. Use the old app's Export button to open its native Save dialog. Before expanding the scenario, prove a small process-owned UI Automation helper can identify the dialog, enter an owned destination and invoke Save/Cancel through the actual controls. Retain the input trace and independently inspect the destination. Close via the owned window's normal close action and await exit; destroying a driver session or killing the process does not establish normal close.
5. Once that capability succeeds, complete old-UI export, direct candidate NSIS upgrade at the same destination, candidate-UI import/review/confirmation, explicit switch, normal close and reopen. Use the existing [stage-specific fixture validators](../../../../../scripts/development-package-fixture.mjs), including exact UUID/payload preservation and the expected no-Steam-account launch-sync result. Match the installed candidate executable to the built payload. A separate fresh candidate installation is an additional case, not implied by upgrade success.

## Desktop boundary and stopping condition

Edge WebDriver cannot operate native Windows UI; Microsoft names UI Automation as the complementary mechanism. Use PID/owner-bound controls and standard UIA patterns or verified native keyboard input for Open/Save and close. Read-only DOM observations and screenshots can establish what rendered, but cannot substitute for those inputs. [Microsoft native-UI boundary](https://learn.microsoft.com/en-us/microsoft-edge/webview2/how-to/webdriver#step-4b-attaching-microsoft-edge-webdriver-to-a-running-webview2-app).

A hosted desktop limitation is not proven merely by a blank capture. Windows services normally use a noninteractive window station; record the actual session/window station and retain an activated, settled window capture. Tauri's GitHub example supports WebDriver, but does not guarantee native-dialog automation on every image. If the process-owned dialog cannot receive input, stop that scenario and report installer/WebView2 stages separately, with the native round trip unverified. Do not add RDP, autologon, service-policy changes or a player-machine fallback. [Microsoft interactive-service limits](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services).

No hard blocker to this hosted experiment was found. The concrete setup blocker is naive elevated environment overrides; the unresolved capability is native-dialog interaction on the selected runner image. Keep signed production self-update, actual updater UI handoff, Authenticode/SmartScreen, interactive installer pages, standard-user Windows desktop coverage, screen-reader speech and real Steam/TF2/Cloud behavior outside any resulting pass. Cleanup must stop only owned processes, restore policy values and record failures; forced cleanup never converts an incomplete UI stage into success.
