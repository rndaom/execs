## Problem and implemented checks

The previous `scripts/smoke-packages.mjs` wrote a text sentinel, checked it before application startup, and reported `packagedStartup: true` after ten seconds of process survival. Linux also searched for an `execs` window title. Those assertions could pass with lost profile data or an unusable webview.

The harness now seeds two schema-1 profiles, one active and one inactive with a HUD. Their 12 manifest payload references cover user cfgs and binds, launch options, an ordinary mod record and VPK, saved HUD options and HUD files, and one shared base VPK. There are 11 stored payload files across the two profiles and shared store. The synthetic live tree exactly projects the active profile, so no user change needs absorbing at startup.

The manifests and all payload bytes come from the actual tagged v0.1.8 exporter fixtures. The on-disk index, IDs/names, settings and synthetic install are authored inputs, not an installer-created library. [The first-class fixture](../../../../../scripts/fixtures/package-smoke-v018.json) records the tagged revision and original archive hashes. Release execution does not depend on this documentation directory.

Preservation is checked before installation, after preparation of the previous package, after the signed upgrade and Windows installer restart, and after each deliberately launched candidate process has stopped. The checks compare every library path and payload hash, all profile identities/records/launch options, the confirmed root, and every synthetic live file. Added files and unfinished journals fail. JSON formatting and only explicitly named additive default metadata are allowed; nonempty preloader selections, changed HUD options, a false launch-sync success or unrecognized metadata fail. The allowed additions are recorded in each result. This does not forbid ordinary application migrations globally; it defines what is expected for these exact fixtures with no user edits.

The existing signed updater probe, installed Windows version check, full AppImage replacement hash, notices, `.deb` installation/version and AppImage host-Wayland checks remain. Results include candidate and previous package hashes, GitHub source revision and run identity. The previous AppImage hash is captured before its file is replaced.

`result.json` records process survival and the Linux window-name observation separately. `renderedWebviewUsable`, `previousVersionUiReadAndExport` and `candidateUiImportAndSwitch` remain explicitly `not-verified`. It no longer emits a blanket packaged-startup or user-data success. The Linux window name is not semantic readiness or proof of usable content; Windows currently has no window-content assertion.

## Isolation

The script requires GitHub CI and an absolute `RUNNER_TEMP`, creates a fresh direct child named `execs-package-smoke`, and refuses reuse. All authored settings, libraries and live fixture files are beneath that directory. Child `APPDATA`, `LOCALAPPDATA`, `XDG_DATA_HOME` and `XDG_CONFIG_HOME` are isolated. Payload and metadata checks refuse linked trees or redirected fixture roots.

Environment overrides alone do not isolate Steam Cloud. Before downloading or installing anything, the script checks the same Windows registry and Linux HOME/XDG/Flatpak/Snap Steam discovery candidates as `core/src/finder.rs`, and refuses any existing candidate. It also refuses an existing execs, Steam or TF2 process. These are conservative preconditions for the workflow's disposable hosted runners, not a general-purpose sandbox or a reason to run this on a player's machine. Changes to product account discovery require corresponding harness review. The harness never passes game-launch commands or writes a real Steam account fixture.

## Remaining RND-251 evidence

The current native app does not expose a supported readiness signal for this harness. The old `v0.1.7` `scripts/qualification/files/packaged-worker.mjs` used Windows WebView2/CDP and Linux `tauri-driver`/WebKit automation to qualify a worker; it is absent from the current tree, required additional runner tooling and a Windows browser policy setup, and was not restored or treated as current proof. No production test IPC or browser-security relaxation was added.

Required next evidence remains the actual signed NSIS upgrade, AppImage update and `.deb` first-install runs on the candidate, with installer hashes and native screenshots or semantic interactions proving rendered content, old-profile readability, export/import/switch, and persistence after restart. The app's real update lifecycle, including stalled or failed payload handling, needs its own native proof; successful example probes cannot establish that. Profile migrations beyond these two authored library cases, native dialogs/close behavior, Steam-running reconciliation, Cloud acknowledgment and retail engine behavior remain separate requirements. Nothing here authorizes a release or closes RND-251.
