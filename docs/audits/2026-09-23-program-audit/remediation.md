- **D8 (open):** The native reqwest resolver now rejects private or reserved answers for approved download hosts at direct connection time, after the bounded precheck. It delegates other hostnames so configured local/private proxy hosts remain usable. A local DNS-change fixture proves direct rebinding to loopback opens no socket; a fake CONNECT proxy fixture proves `localhost` remains reachable and receives the destination hostname. The original 22 focused network tests, the full Rust workspace, Clippy, and the ignored live GitHub release-metadata smoke passed. A subsequent 23-test focused run also passed, including authenticated HTTP CONNECT and NO_PROXY regression fixtures. [Reqwest's DNS overrides](https://docs.rs/reqwest/0.12.28/reqwest/blocking/struct.ClientBuilder.html) affect the socket connector; [reqwest 0.12.28's proxy connector](https://github.com/seanmonstar/reqwest/blob/v0.12.28/src/connect.rs) passes the request destination to [Hyper-util's CONNECT tunnel](https://docs.rs/hyper-util/0.1.20/src/hyper_util/client/legacy/connect/proxy/tunnel.rs.html), then uses that same destination's hostname for TLS. The proxy resolves the CONNECT hostname independently. A public connector layer wraps this combined operation and cannot separately replace the CONNECT authority while retaining the original TLS server name. A complete bound-destination route would need a separately maintained HTTP/HTTPS proxy tunnel that sends a validated numeric IP in CONNECT, retains the original hostname for TLS, and covers proxy authentication, exclusion rules, timeouts and streaming. The only narrow fail-closed option with the current reqwest client would reject every intercepted proxy request; that would break legitimate proxy downloads. Proxy behavior therefore stays functional and D8 stays unchecked. No live CDN redirect was exercised by these fixtures.
