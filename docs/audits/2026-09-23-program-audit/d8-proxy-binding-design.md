# D8 proxy destination binding: implementation design

**Status:** Open. This is a design and acceptance plan, not evidence that proxied downloads are bound to a validated address. The direct connection resolver in `apps/desktop/src-tauri/src/net.rs` already rechecks public addresses at socket resolution. The current reqwest proxy path still sends a hostname in `CONNECT`, which the proxy can resolve independently.

## Required invariant

For every approved HTTPS request and each validated redirect, a direct socket must use a freshly checked public address, or a configured proxy must receive a numeric `CONNECT` target chosen from those addresses. A configured proxy may itself have a local or private address. The TLS server name, certificate name check and HTTP `Host` must remain the original approved download hostname. All redirects, authentication, proxy exclusions, time limits and body caps must keep their current behavior. A proxy can ignore its `CONNECT` target or forward traffic elsewhere; the client cannot prove the proxy's actual outbound socket address. Numeric `CONNECT` removes independent proxy DNS resolution under a conforming proxy, and origin TLS verification still protects the hostname.

The proxy case needs two independent names: a validated numeric `CONNECT` target and the original URL hostname for TLS. Reqwest 0.12.28 passes the same destination URI to [Hyper-util's CONNECT tunnel](https://github.com/seanmonstar/reqwest/blob/v0.12.28/src/connect.rs#L793-L877) and then takes that URI's host for TLS. Its public [`dns_resolver` and `resolve_to_addrs`](https://docs.rs/reqwest/0.12.28/reqwest/blocking/struct.ClientBuilder.html) affect socket resolution, which is for the proxy host on a proxied request. The public `connector_layer` wraps an opaque service and does not expose a way to set the two names separately. Rewriting the request URL to an IP would also change TLS hostname handling. Rejecting all proxy requests would close the route by breaking legitimate downloads. Neither is an acceptable D8 fix.

The [newer reqwest 0.13.5 source](https://github.com/seanmonstar/reqwest/blob/v0.13.5/src/connect.rs#L819-L827) still passes `dst.clone()` to the tunnel and derives the rustls server name from `dst.host()`. Its [public builder](https://docs.rs/reqwest/0.13.5/reqwest/blocking/struct.ClientBuilder.html) still exposes DNS overrides and the opaque connector layer, rather than an independent CONNECT authority. A routine 0.12-to-0.13 upgrade does not supply the needed hook.

## Candidate transport

The [libcurl `CURLOPT_CONNECT_TO` contract](https://curl.se/libcurl/c/CURLOPT_CONNECT_TO.html) is a fit worth testing: it changes the connection host/port, including an HTTP proxy tunnel destination, while retaining the URL's host for TLS SNI, certificate validation and application protocols. Its [Rust binding](https://docs.rs/curl/0.4.50/curl/easy/struct.Easy2.html#method.connect_to) exposes this option. This is a proposed migration, not a verified replacement for the present client.

1. Retain the source-specific URL/host/path rules in `net.rs`. For each hop, resolve the original hostname under the bounded DNS deadline. Reject empty or mixed public/non-public results. Select a public address and configure `connect_to` for that host and port only, using `[IPv6]` syntax for IPv6 addresses. Preserve an explicit port (currently only default HTTPS/443 is admitted). A connection failure may try the other checked public addresses; it must never fall back to proxy-side hostname resolution.
2. Keep the original HTTPS URL on the transfer. Enable peer and hostname verification for both the origin and an HTTPS proxy. Never set a numeric IP as the URL host. Disable automatic redirects and validate each `Location` before resolving and binding its next hop. Do not reuse a connection when its binding would differ from the new hop.
3. Let libcurl select [environment proxies](https://curl.se/libcurl/c/CURLOPT_PROXY.html) and [NO_PROXY exclusions](https://curl.se/libcurl/c/CURLOPT_NOPROXY.html), while checking parity with the current reqwest behavior on Windows and Linux. Cover HTTP and HTTPS proxies, URL basic credentials, direct exclusions, and authenticated proxy responses. Do not silently bypass a configured proxy or discard its credentials. The app's pinned `reqwest` build uses environment variables for its automatic “system” proxies; it does not read an OS proxy settings API.
4. Apply the existing 5/30-second connection and 20/600-second total policies, including the remaining deadline across manual redirects. Stream response chunks into a size-limited collector; refuse a declared or actual oversize body before caching, and keep existing digest/magic validation. Bound response-header parsing and distinguish origin headers from proxy CONNECT headers.
5. Pin and package the chosen libcurl implementation deliberately. The [curl Rust binding's build guide](https://github.com/alexcrichton/curl-rust#building) documents dynamic system linking by default and optional bundled/static builds; its TLS backend differs by platform. Check the actual Windows NSIS, Linux AppImage and `.deb` dependency inventories and HTTPS proxy support, not only local `cargo test`. The binary must not depend on an unbundled library absent from a supported install.

This is broader than a `net.rs` option change. `hud_fetch.rs`, `hud_stats.rs` and other fetchers currently pass or type `reqwest::blocking::Client`, while `net.rs` returns `reqwest::blocking::Response` from its shared request path. A clean migration needs an owned transport/client response abstraction and a caller sweep. Keeping the reqwest client parameter while secretly using libcurl would hide the change in proxy, timeout and trust behavior. The current release and package-smoke workflows do not explicitly install or assert a libcurl runtime dependency; a dynamic Linux build might work on the CI image and still fail on a user host. Static versus dynamic selection, TLS roots and library notices need explicit package decisions before product integration.

## Acceptance evidence before checking D8

- A fake authenticated HTTP proxy records `CONNECT <validated IPv4>:443` and `CONNECT [<validated IPv6>]:443` for two approved hostnames. It never receives the original hostname as target. Separate origin TLS fixtures observe the original SNI and HTTP `Host`, accept a matching certificate and reject a mismatched certificate. A proxy that forwards the numeric target to a private test server with a mismatched origin certificate must fail TLS verification.
- An HTTPS proxy fixture verifies both proxy TLS and origin TLS, with distinct names and trust chains. An invalid proxy certificate, wrong authentication and a 407 response fail clearly. `NO_PROXY` sends no CONNECT to the proxy and still uses the guarded direct resolver. Tests cover the supported variable precedence on Windows and Linux.
- A redirect fixture tries an allowed first hop followed by a private DNS answer, a disallowed host, non-HTTPS URL and unexpected port. Each is refused before a second network connection. A valid multi-hop redirect binds each hop independently; a changed DNS answer cannot make the proxy choose a private destination.
- Connection stalls, proxy tunnel stalls, origin body stalls, oversized `Content-Length` and streaming overflow honor existing time and byte limits. Cache verification still rejects bad bytes and failed writes. Existing native network tests, workspace fmt/Clippy/tests, and the packaged Windows/Linux smoke matrices pass.

**Current conclusion:** The current reqwest client has no supported hook for independent CONNECT target and origin TLS name. The libcurl route is source-backed but remains unimplemented and unqualified here. Keep D8 unchecked until the transport and acceptance evidence above exist.

## Bounded transport probe — September 24, 2026

The [loopback-only fixture](d8-curl-probe.py) used the Windows **`curl.exe` CLI**, linked to libcurl **8.21.0 with Schannel**, and an ephemeral test CA. The fake HTTP proxy acknowledged CONNECT without dialing any public address, then served a short HTTPS response on the same local socket. It observed numeric `CONNECT 1.1.1.1:443` and `CONNECT [2606:4700:4700::1111]:443`, Basic proxy authentication, and the original `example.com` SNI and `Host` on both requests. A matching origin certificate passed; a wrong-name certificate was rejected with curl error 60 before any HTTP request. The fixture uses `--ssl-no-revoke` only on Schannel because its ephemeral CA has no revocation endpoint; it does not change product TLS settings. Command: bundled Python `docs/audits/2026-09-23-program-audit/d8-curl-probe.py`. All three assertions passed locally and passed again on an independent run by the root agent.

The [audit-local Rust curl-binding prototype](d8-rust-curl-prototype/README.md), with pinned `curl` 0.4.50 and bundled `curl-sys` 0.4.90/libcurl 8.21.0, then built on Windows with `cargo build --locked` and passed the same loopback fixture through `--rust-client`: numeric IPv4 and bracketed IPv6 CONNECT, Basic auth, original SNI/Host, matching TLS certificate, and wrong-name certificate rejection. The prototype is standalone and does not change product dependencies or code.

These runs demonstrate the CLI and Rust binding's local transport semantics, not product integration, live proxy selection, `NO_PROXY`, HTTPS proxy TLS, redirect-by-redirect validation, timeout or cap behavior, Linux operation, or packaged NSIS/AppImage/`.deb` support. Those remain D8 acceptance work.
