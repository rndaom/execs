# D7 — stock Viewmodels compatibility bridge and local rebuild boundary

**Status: feasibility evidence; D7 remains open.** The current Viewmodels builder reads CompVMInstaller QC/SMD sources, rewrites selected sequences, and compiles a VPK with the player's `studiomdl.exe`. This check asks whether the 64 saved `yttrium-1` choices at least have exact targets in the player's installed TF2 models. It does not derive new group semantics from those models or prove a rendered replacement.

## Verified name-level bridge

On September 24, 2026, [`d7_legacy_stock_overlap.py`](d7_legacy_stock_overlap.py) read the confirmed app-440 install at patch `10828683`. It required `tf2_misc_dir.vpk` SHA-256 `63f7db0d1c509e303ca9002fee9e3d805e9220ea5afdd639d8a6b68b8a3710b9`, checked the nine class MDL entries against the VPK directory CRCs, and parsed their bounded metadata. It then compared the existing [64-group table](../../../apps/desktop/src-tauri/core/src/viewmodel_groups.rs), SHA-256 `69a4e46532cba89e0b3bc3af8957ac7021ee0483e15345ced0618cd6e11da4f9`, with those **installed** models. Valve's [`mstudioseqdesc_t`](https://github.com/ValveSoftware/source-sdk-2013/blob/b8cfb12c0e083a2ef5b2f9f9b50f3902fa034474/src/public/studio.h#L3404-L3472) defines the sequence label and its local-animation blend indexes; the [existing bounded MDL parser](d7_stock_mdl_probe.py) checks those pointers before use.

Every one of the table's **405 distinct class/sequence stems** has exactly one same-named stock sequence, exactly one local animation named `@<stem>`, and exactly one blend index pointing to that animation. These names match with exact case. The six extra Soldier Original stems in `SOLDIER_FORCED_FILES` also pass. There are no duplicate stems across legacy groups within a class. The new comparison check's five synthetic tests reject a second blend, a wrong referenced animation, duplicate sequence labels and case-only mismatches. It reads game files only; it writes no model, profile or repository asset bytes. Reproduce with the confirmed TF2 root:

```powershell
$py = '<Python interpreter>'
$tf2 = '<confirmed TF2 root>'
& $py -B docs/audits/2026-09-23-program-audit/d7_legacy_stock_overlap.py $tf2 --expected-vpk-sha256 63f7db0d1c509e303ca9002fee9e3d805e9220ea5afdd639d8a6b68b8a3710b9 --expected-patch 10828683
& $py -B -m unittest discover -s docs/audits/2026-09-23-program-audit -p test_d7_legacy_stock_overlap.py -v
```

This is a **compatibility comparison** with a CompVMInstaller-derived table, not an independent source for the future group definitions. It establishes that a proposed local model transformer can address every saved legacy sequence by exact identity on this one TF2 patch. It does not prove that an item reaches that sequence, that a binary edit hides the rendered model, that the sequence has no layers or procedural effects, or that a later TF2 patch retains these names. The [independent item-to-activity study](d7-stock-mapping-study.md) and [Scout weapon-bone scratch candidate](d7-scout-weapon-bone-probe.md) cover different prerequisites, with no retail behavior result yet.

## Decision for a replacement prototype

The technically testable route is to derive a fresh item/activity/group graph from installed TF2 schema, scripts and MDLs; freeze it before consulting the old table; then validate an exact old-ID to new-selection mapping against this 405-stem bridge. A local builder could copy the verified stock animation MDLs into bounded staging, transform only selected local animations, validate the resulting model and VPK, and install through the current profile transaction. This would avoid the CompVMInstaller source ZIP and Windows-only `studiomdl` compilation **if** a safe binary transform is established. The Scout scratch checks show limited structural feasibility, not product readiness. Full-hide and hands-visible variants, all nine classes, combined selections, updates and retail TF2 behavior remain unverified.

The output VPK must also stay out of a **shareable** profile ZIP unless its redistribution basis is resolved. Valve's [TF2 Mods FAQ](https://partner.steamgames.com/doc/sdk/uploading/distributing_source_engine?l=english) says TF2 mods may load TF2 content from a local install but may not redistribute TF2 game files; whether a transformed MDL counts as a redistributable own file is not settled here. Today's [profile exporter](../../../apps/desktop/src-tauri/core/src/zip.rs) copies every manifest file, and its import validator requires a verified VPK when a Viewmodels record exists. A source-specific recipe export would need a new stock-derived provenance marker, selected group IDs/mode, exact input identities, pending local rebuild on import, and a fail-closed switch when source files are absent or changed. Existing imported VPKs and legacy `compiled` profiles must remain readable and retain their approved bytes. The [Valve export review](d7-valve-export-rights.md) records this separate product and rights change.

**Next decisive experiment:** after establishing a confined visual test environment, build one selected Scout sequence from a copied stock MDL, render its included `c_scout_arms` parent with the relevant weapon, then test it in retail TF2 alongside unchanged sequences. Repeat for weapon-only and full-hide modes before extending to 64 groups. A structural name match alone is insufficient to check off D7.
