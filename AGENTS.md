# execs — project guide for agents and contributors

execs is a Windows + Linux desktop companion for Team Fortress 2 (Tauri 2, Rust core, React/TypeScript UI). It keeps a player's whole customization surface as named **profiles** and switches between them while the game is closed. This file is the working spec: durable decisions live here, in present tense. Add a line when a decision is made; delete lines that stop being true.

## Repo

```
apps/desktop/            Tauri app (the product)
  src/                   React UI: one file per pane, lib/ (pure logic + tests), hooks/, components/ui/
  src-tauri/src/         Tauri crate `execs`: commands/ (IPC), net.rs, *_fetch.rs, gamebanana.rs, hud_stats.rs
  src-tauri/core/        `execs-core`: everything that touches disk, no Tauri/WebKit
packages/cfglint/        Source cfg parser/linter (TS), used by the Files pane
tools/promo/             Text-only Remotion promo; outside the pnpm workspace (`pnpm install --ignore-workspace`)
docs/media/              Development preview screenshots and the text-only promo GIF
docs/RELEASE.md          Public vs dev, versioning, cadence, ship checklist
CHANGELOG.md             User-facing notes; the release workflow reads this
.github/workflows/       ci.yml (frontend, rust-linux, rust-windows), release.yml (tag → draft → verify → publish)
```

Commands: `pnpm install`, `pnpm desktop:dev` (Tauri), `pnpm dev` (browser only, fixture data via `?preview=<state>`; states in `src/lib/preview.ts`), `pnpm test`, `pnpm check` (biome), and for Rust `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace --locked` with `--manifest-path apps/desktop/src-tauri/Cargo.toml`. CI runs all of these; keep them green. `.npmrc` `node-linker=hoisted` is required on Windows. Vite defaults to port 1420 (`EXECS_DEV_PORT` moves it; `tauri.conf.json` `devUrl` must match). Plain `package.json` scripts only; source and cfg fixtures use LF (`.gitattributes`), while archived CI evidence retains its original bytes for provenance checks.

## Architecture

- Inventory is a read-only development pane, hidden in production frontend builds and refused by release native commands. Steam access runs in a bounded child process through the existing signed-in session; only ClientHello and account-bound cache refresh messages are sent. The pane automatically reads a snapshot on first visible, focused use, then every two minutes while active and after TF2 closes. Reads never overlap, pause while hidden, unfocused, busy or in-game, and back off failed connections from 30 seconds to five minutes. Same-account refreshes preserve browsing state and cached artwork; account changes reset that state. Failed refreshes retain explicitly stale snapshots and offer Retry. Inventory and future layout drafts belong to the Steam account, never a customization profile; switching profiles must not rearrange items. The pane shows the signed-in Steam persona and avatar, with one page control, five-column 50-slot pages, TF2 quality borders and view-only name/quality/type sorting. Names, kit and fabricator targets, wear tiers and effect labels come from bounded item attributes and installed TF2 metadata. War paints show the installed item icon with a separate installed pattern swatch when available; the preview does not reproduce in-game material mapping, wear or effects. Killstreak kits pair their kit art with the target item's icon where installed metadata provides it. Inventory art loads in bounded batches, uses suitable VTF mip levels, and treats oversized optional artwork as an item-level omission. Full item attributes and live backpack rearrangement remain future work, with a safety plan in `docs/design/2026-09-22-overhaul/implementation/inventory/rearrangement-plan.md`. Jengerer's Item Manager inspires the interactions and is credited; its unlicensed code/assets are not reused. This is future minor-release work, not assigned to 0.2.0 yet.

- **Core owns disk, the crate owns network, the UI owns drafts.** `execs-core` has no networking; `*_fetch.rs` / `gamebanana.rs` download through `net.rs` (one client, `execs/<version> (+https://github.com/rndaom/execs)` user agent, size caps, pinned URLs, sha256 where the source publishes one). Commands in `src-tauri/src/commands/*` are thin: `blocking` / `with_root` / `with_profile` run work off the main thread; writes take the `WriteGate` mutex.
- Native fetches use the owned libcurl client in `net.rs`: every approved HTTPS hop resolves and rejects non-global addresses, then binds direct connections and proxy tunnels to a vetted numeric address while retaining the URL hostname for TLS and HTTP. Redirects are checked separately; the shared client reuses a connection only for the same host, vetted address and proxy settings.
- Configured proxy hosts retain their normal DNS resolution. The scoped D8 binding review passed Windows/Linux product proxy fixtures and hosted native/package checks. Debian packages declare OpenSSL/zlib runtime dependencies; the AppImage bundles OpenSSL and uses host zlib under AppImage's base-library policy. Live CDN redirects and installed-candidate upgrades remain release checks.
- **Errors** are `{ code, message }` (`error.rs`); the frontend's single `call<T>()` in `lib/bridge.ts` turns them into `BridgeError`. Every command has a preview twin in `lib/preview-bridge.ts` (the `Api` type is derived from `bridge.ts`, so a new command cannot be forgotten there).
- **Record contracts:** `execs-core` `contracts.rs` serializes fully populated `ProfileDetail` (with HUD, crosshair, viewmodel recipe, hitsound and every mod source) and `ProfileLibrary` into `apps/desktop/src/lib/contracts/*.gen.json`; `lib/contracts.test.ts` checks those fixtures and the preview twins against the bridge types with compiler-checked key lists in both directions. Changing a serialized record means updating the TS type and regenerating with `EXECS_UPDATE_CONTRACTS=1 cargo test -p execs-core --lib contracts`.
- **Pane logic lives in `lib/*-ui.ts` with unit tests**; components stay thin. Drafts use `useSeededDraft` keyed by profile id so a switch never leaks a draft into another profile.
- **Crash hardening:** no `panic = "abort"`; panics log to `<data dir>/logs/panic.log`; the lock poller wraps each tick in `catch_unwind`; heavy work never runs on the main thread.
- **Data dir:** Windows `%AppData%\execs`, Linux `$XDG_DATA_HOME/execs` or `~/.local/share/execs` (`settings.json`, `profiles/`, caches per feature, `preloader/originals` snapshots, `logs/`). Not Tauri's app-data dir.
- App settings Health (`execs-core` `health.rs`, `get_install_health`) is read-only: confirmed root, active cfg layer, pending switch/profile/Casual journals, per-profile missing library bytes (stat only) and uncached direct-author Casual downloads, the picked Steam account's local Cloud `config.cfg`, HUD catalog cache age and legacy library presence. Unreadable evidence is unknown; a local Cloud copy is never described as a confirmed upload; no Steam verification or fetch starts.

## Integrity rules

- The file-safe surface is `tf/custom/`, `tf/cfg/overrides/` (or the vanilla `tf/cfg` user files when mastercomfig is absent), and TF2's Steam Cloud `config.cfg` copy. Nothing else is written, with one exception below.
- **Never** write `tf/cfg/user/`, `tf/steam.inf`, or anything while the game runs. Never store `-autoconfig`, `-default`, `-dxlevel`, `+quit`, or `gamemoderun %command%` on a profile. Never write `localconfig.vdf` while Steam runs.
- **Write lock:** process name `tf_win64.exe` (Windows), `tf_linux64` or `tf_win64.exe` under Proton (Linux). `refuse_if_running()` guards every live-surface and library write; app-data settings writes stay allowed.
- **Preloader exception (Mods pane):** `gameinfo.txt` gets only the reversible `type multiplayer_only` ↔ `//type` toggle, pristine copy backed up first; `particles/*.pcf` DATA is patched in place, size-preserving, inside the sibling `tf2_misc_*.vpk` archives. **The `_dir.vpk` is never written, not even a CRC**: the directory carries Valve's tree checksum and sv_pure validates against its stock CRCs, so a rewritten CRC makes pure servers reject the whole archive (magenta everything). Every patched entry is snapshotted first; Restore stock files puts every byte back.
- Every write to a file that matters goes through `hash::write_atomic` (`<file>.execs-part` then rename). Absorb repairs a write that was cut off mid-copy (see Profiles).

## Profiles

- A profile = user cfg layer + `tf/cfg/config.cfg` + all of `tf/custom/` + launch options + records for HUD, crosshair, viewmodel, hitsounds and mods. Library at `profiles/<uuid>/` with `manifest.json` (per-file sha256), exclusive trees, `mastercomfig-base.vpk` shared by hash. Export/import is a zip.
- There is no community hub and no profile uploads. Sharing is the export zip, sent however the player wants.
- Import also accepts creator ZIPs with `cfg/` and/or `custom/`, at the root or inside wrappers (including `tf/`). One cfg tree and multiple custom trees can be combined; destination collisions still fail. Missing `config.cfg` is seeded from the confirmed install's `config_default.cfg`, and legacy `<pack>/UI/{hit,kill}sound.wav` files move to `execs-hitsounds/sound/ui/`; review notes disclose both. Optional variants outside the cfg/custom layout and launch-option instructions stay in the source ZIP. A review names the new profile, counts imported/skipped files, and flags cfg commands before explicit trust; approved cfg bytes (including flagged saved server credentials) stay unchanged. Archive/path/parser limits always apply, native exports retain strict validation, and credential-bearing bytes are disclosed before a player shares an export. Import never activates the new profile or merges in the current setup; its result stays visible until dismissed or switched.
- Source rejects loose outer custom folders named `materials`, `maps`, `resource`, `scripts`, `sound`, or `models` without case sensitivity. Mod/HUD imports allocate safe outer names; native profiles retain their original paths until the user reviews Repair folder names. Repairs preserve payload bytes, use the profile transaction and excluded HUD backup container, and refuse active live drift or selected particle sources that would lose their mod identity. A same-named `.vpk` remains valid.
- Folder repairs remap profile-owned saved particle selections together with their mod records, including inactive profiles. A profile that still owns installed particle sources must restore or clear that projection before repair; other profiles' saved selections and shared projection stay unchanged.
- Profile export scans cfg members inside Source-signature VPKs through the bounded parser and binds inspection and copying to the manifest hash. Before export, a revision-bound review counts the included custom packs, lists up to 50 pack roots with file counts, flags Crosshair scripts and Viewmodels VPKs, and names possible saved-credential locations. It does not remove or license any bytes in the ZIP. Credentials are preserved with the player's own cfg bytes; malformed signed VPKs, parser limits and source changes refuse export without replacing the destination. Legacy files without the four-byte Source signature stay opaque; they still require exact hashes and normal archive limits.
- **Switch is exact replace, not merge.** Sources are validated before the Remove step, files are written atomically, the active id flips last; a failure after Remove clears the active id and the UI says re-apply. Previous exclusive files are removed only when the live hash still matches.
- Switching away from a profile with still-installed Keep packs requires capturing them into that profile or removing them first; no target replacement or unowned pack carryover occurs. Deleting an active profile with Keep installed leaves a durable handoff marker; Save current as… captures the retained setup before another profile can switch in.
- **Absorb** runs on boot and after TF2 quits: owned-file and `config.cfg` drift goes into the active profile automatically (Cloud copy dual-written); new or deleted packs prompt with Update (default), Restore removed, Keep. Keep is remembered in `ignored_packs`; Update clears it. Never silently roll the live folder back.
- Custom inventory fails on unreadable files or directories instead of inferring deletion. Absorb commits additions and removals together, matches full manifest paths without case sensitivity on Windows, and refuses live paths that collide under portable profile identity on any platform.
- Absorb reconciles touched mod records and file/byte totals in the same library transaction as accepted inventory changes. Confirmed HUD removal clears its selected record; Keep, Restore, unreadable inventory and inactive saved packs do not imply deletion. Managed sound/viewmodel packs retain interrupted-write self-repair.
- Accepted ordinary external packs receive stable `External` Mod records while retaining their original folder or VPK names, including through export/import. Accepted drift to managed crosshair, viewmodel or hitsound payloads marks the saved source unverified; a change to crosshair CVars in the Gameplay cfg does the same. Unrelated Gameplay values do not change crosshair provenance.
- **Junk is never a pack:** `*.execs-part`, and Steam's own `tf/custom/readme.txt` and `workshop/`, are ignored everywhere. **Self-heal:** before classifying, absorb rewrites any manifest file missing from the live tree when its `.execs-part` sibling exists or the pack is app-owned (`execs-*`), deletes stray part files, and drops those keys from the ignore list (field incident: the dev app restarted mid-switch and left a half-written viewmodel pack).
- `tf/custom/execs-preloader.vpk` stays outside ordinary pack inventory (`GLOBAL_CUSTOM_FILES` in `surface.rs`), but its addon/particle selections belong to the profile. Switch validates and replaces this shared projection, restoring old particle patches before publishing the target id. A preloader journal inside a pending switch rolls back before that switch retries. Legacy global selections migrate only to previously recorded preload profiles; imported profiles default to empty selections. Profile exports carry these selections.
- Profile ZIP imports use the themed review modal and real read/review/save progress. The backend retains the source path and exact-byte review behind a single-use token; confirmation rechecks the root, write lock and ZIP hash. Cancelling a review writes no profile.
- The switch progress panel shows only real steps (game closed → pack current → remove → write → Cloud → done), paced to a minimum display time; never invented steps or percentages.
- Restore points (`execs-core` `restore_points.rs`) are verified native profile exports in `<data dir>/restore-points/<token>.zip` with `<token>.json` metadata (profile id and name, optional label, strictly increasing millisecond time, size) written after the ZIP; a ZIP without metadata is unlisted and cleaned by the next save. Saving is a library read under the library-read gate and allowed while TF2 runs; unabsorbed live edits are not included. Retention (`retention.json`, 1–20, default 5, UI offers 3/5/10) removes the oldest per profile only when saving or changing the bound; points of deleted profiles stay listed until removed. Compare reads the ZIP manifest and managed cfgs without extraction; Restore imports through the native import path under a new name as an inactive profile, scanning cfg bytes with the same trusted mode export used (a shared ZIP from someone else keeps the stricter scan) (write lock, recovery refusal, stock-built rebuild checks). Recovery journals are separate and never pruned here. There are no automatic restore points yet.
- Rename changes only a profile's display name, inline from its action menu, through the ordinary journaled profile transaction (manifest and index together). The UUID, files, shared blobs, records and active tracking are unchanged and nothing in TF2 is written. Names follow creation rules (trimmed, 1–80 characters, duplicates allowed) plus the import rule against control characters; the library write lock applies.
- Duplicate copies a saved profile into a new inactive profile with a fresh UUID, asking only for a name (default "<name> copy"). It reads library bytes only: exclusive files are copied, shared blobs are referenced, each copy must match the source manifest hash, and live drift is never included. HUD/crosshair/viewmodel/sound/mod records, launch options, ignored packs and preload selections come along; Steam launch-option projection starts pending. Creation stages everything and publishes the index last, so a failure leaves no partial profile. Profiles that need folder repair cannot be duplicated.
- Compare with current… (`execs-core` `profile_compare.rs`, `compare_profile_switch`) reads the active and target library manifests plus their managed Gameplay/Binds cfg bytes: HUD, hit/kill sound names, redacted launch options, top-level custom packs and `tf/cfg` files by combined hash, config.cfg (with its local Cloud copy noted separately from Steam's upload), managed values and Casual choices, and whether the target switch preflight would refuse. Credential commands are never returned. Switch from the dialog re-reads the comparison and shows it again if either manifest revision changed; the switch itself keeps every existing guard. One-click switching from the list is unchanged.
- Profile deletion is an explicit library operation with Export first and Cancel available. Deleting the active profile requires either switching to another profile first or keeping the installed setup and clearing its tracking; deleting the last profile keeps the installed setup. The index is the deletion commit point, a bounded journal makes interrupted cleanup recoverable, and deletion never removes TF2 files. Draft and write-lock guards remain mandatory.

## First run

Find TF2 through Steam library folders (registry, `libraryfolders.vdf`, `~/.steam`, Flatpak, Snap), accept only a root whose `tf/steam.inf` says app 440, always offer Browse, remember the root only after Confirm. Existing customization → **Save current as…** only. Unused install → the setup wizard (name, preset, official addons). Create new profile reuses the wizard with **Start from: Current setup** (copies the active live `config.cfg` verbatim under the write gate, including edits since the last absorb, so no tutorial pop-ups) or **Fresh TF2** (Valve's `config_default.cfg`). No silent write before the path is confirmed.

## Panes

- **Comfig** — offers mastercomfig's current Ultra, High, Medium, Low and Custom presets, modules and official addons through our UI. Removed Medium High and Medium Low and delisted Destitute remain readable on existing profiles but are not offered for new selection; no legacy choice changes automatically. VPKs come from mastercomfig's GitHub releases; writes `tf/cfg/overrides/{setup_hook,modules}.cfg`. Extras and the preset guide open in an in-app `WebviewWindow` with no IPC. Credit comfig.app; never brand as official.
- **Binds** — click-to-record for the usual actions; writes `execs_binds.cfg`. Standalone, uncommented binds for known actions in that file belong to the pane; sync and recording retain every other line byte-for-byte. Actions are grouped by player task under an All view with category tabs and a search that matches action names, player words and bound keys. Each action shows its inspected startup keys as readable key caps; the CFG line that last assigned a key is in its tooltip and accessible name, and every key offers remove. Voice-command actions use `voicemenu <menu> <item>` from the pinned dump. Recording adds a key without silently removing other keys; a key already running a different command requires review before its new assignment. Remove leaves the key running nothing: it deletes the pane's own line when nothing earlier binds the key, otherwise it writes one standalone `unbind <key>` (also pane-owned) so an inherited `config.cfg` binding never comes back; a key a later startup cfg binds again is explained and left unchanged. Recording the key again replaces that unbind, and the after-game sync drops it only when TF2 bound the key again. Class, launch and in-game commands may change the runtime result. Autoexec exec lines are addressed from `tf/cfg` (`exec overrides/execs_binds`): the engine resolves `exec` per search path, so a bare stem inside `overrides/` silently fails (field bug). No alias studio, no generated `unbindall`.
- **Gameplay** — world FOV, tracers, mouse sensitivity, weapon and combat-feedback comfort toggles; writes `execs_gameplay.cfg`, and links to Viewmodels for viewmodel settings. Transparent viewmodels is an addon VPK toggle, never a cvar.
- Mouse `sensitivity` and `zoom_sensitivity_ratio` are exact decimal fields owned by the Gameplay scope (native `managed_cfg` and the frontend scope agree); input accepts plain positive decimals up to 1000 because the pinned dump documents no range, and an invalid entry is shown with a reason but never saved. Because the managed cfg runs after `config.cfg`, a completed absorb that saw `config.cfg` drift rewrites only the managed lines when TF2's options changed them; the sync never adds lines the managed file did not set. Raw input and acceleration stay with mastercomfig's Flat mouse addon, and no recommended sensitivity is offered.
- Gameplay's Weapons group holds auto reload, fast switch and Medigun auto-heal (`tf_medigun_autoheal`); Combat feedback holds damage numbers, combined damage numbers and healing numbers (`hud_combattext`, `_batching`, `_healing`). All are archived client cvars with no sv_cheats or server requirement; values seed from the effective cfg and TF2's defaults apply only when absent. Colors and the batching window are not offered. The same after-game sync covers these toggles, auto reload and fast switch because TF2's Advanced options write them to `config.cfg`; it accepts only values those options would write.
- **HUD** — hud-db catalog (paginated, sorted by name / tf2huds.dev listing activity / downloads / views from exact matched statistics, cached a day), one HUD per profile, install kinds by host (GitHub codeload zip, Dropbox `dl=1`, GameBanana download page, teamfortress.tv thread scrape, or link out), import from zip/7z/folder (RAR refused), TF2HUD.Editor schemas consumed as data (parser strips `//` comments, options may lack `Name`). Listing activity is not a HUD release date; missing statistics never enter metric rankings. Imgur albums open in the browser; GitHub `showcase.md` albums load in-app.
- HUD browsing uses six previews per page with numbered navigation and page jumps above and below results; one Import HUD entry offers archive or extracted-folder choices. Imports unwrap a unique nested HUD only when every retained file belongs to it. Multiple HUD roots or sibling files require the user to follow the author's instructions and import one extracted HUD folder. `info.vdf` must declare UI version 3 before install; metadata and payloads are never synthesized or rewritten to imply compatibility. Dropbox download shards are trusted only as Dropbox redirects, one label below `dl.dropboxusercontent.com`.
- HUD/mod ZIP, 7z and folder imports share the profile ownership junk policy: case-insensitive `.bak`, `.cache`, `.ztmp`, `.execs-part`, VCS/OS metadata and `node_modules` components are skipped before root detection. Payload bytes and archive/path limits remain unchanged.
- HUD metric sorts rank only entries with a valid selected statistic; coverage and missing counts are explicit, and A to Z includes the full catalog. Statistics reloads serialize independently of the catalog and report loading/failure. tf2huds.dev counts follow its HUD list, then match explicit comfig links or unique GitHub repositories; names and missing values are never guessed into rankings. Browser fixture data is labeled Preview data.
- HUD option resources use literal-backslash KeyValues for both parsing and serialization; Steam VDF keeps escape processing. Animation comment/uncomment directives edit command lines without parsing animations as KeyValues. Checkbox branches and file-named resource headers follow the schema, errors name the control and relative file, and invalid edits fail before the library/live transaction.
- HUD catalog art uses the same pinned tree revision as the catalog data; showcase albums expire after a day and can be refreshed on demand. A GameBanana HUD page downloads automatically only for one unambiguous ZIP/7z; other file choices route to manual import.
- HUD Editor overlay crosshair glyph choices are distinct from engine Crosshair controls. Unsupported `Special`, `Pulse`, `Shadow`, and unknown schema operations stay visible but unavailable with saved values preserved. e.v.e Plus is schema-supported after the pinned archive and full-option compatibility harness; other catalog overlaps remain gated until their own file operations pass.
- Return to stock HUD is HUD install without a new HUD, behind a themed confirmation that names the HUD and its option cfgs. It removes every HUD root the profile owns (including legacy multi-HUD roots), managed `execs_hud_*` cfgs and their managed autoexec exec lines in one recoverable transaction, and clears the HUD record and roots. On the active profile, mounted HUD folders move beneath the backup container with untracked files; no earlier HUD is reactivated. Other packs, cfg settings and preload selections stay. The write lock applies.
- HUD installed state reads only the local manifest and catalog cache. Schema reads carry the exact profile and HUD identity; stale or failed reads remove controls while same-HUD drafts survive retry. Catalog and statistics results disclose incomplete sources while retaining valid cached entries and values; source-read failures do not turn a committed local import into a failed install.
- HUD ownership uses additive selected-root, retained-root and pending-review metadata. Competing valid UI3 roots require an explicit, fingerprint-bound choice before activation; excluded originals remain outside Source's mounted surface. Legacy journal recovery reads the original manifest identity before normalization. A profile ZIP keeps approved cfg bytes unchanged; choosing another HUD with managed options leaves an inactive profile pending a separate disclosed reset review. That review preserves originals and refuses live cfg/autoexec drift both before staging and at commit. Generic Mods refuses detected HUD payloads with a route to HUD import. HUD VPKs require extracting and importing the actual HUD folder; no metadata or payload bytes are synthesized to imply support.
- **Crosshair** — stock crosshair controls with live previews decoded from the user's own `tf2_textures_dir.vpk`; the custom builder writes `tf/custom/execs-crosshairs/` (VTFs + patched weapon scripts read from the user's `tf2_misc_dir.vpk`, ICE-decrypted in process). New choices come from first-party shapes, the parametric designer and imported PNG. The Venom remote picker and native fetch commands are retired while previously saved VTFs remain selectable and rebuild from profile-owned bytes; missing bytes fail the build without replacing the pack. Tint is cvar-based (`cl_crosshair_red/green/blue`), textures stay white; apply forces `cl_crosshair_file ""`. VTF header: bumpScale@48, format@52, mips@56.
- Crosshair settings preserve unknown external `cl_crosshair_file` values through unrelated edits. Build refuses unreadable or unpatched requested weapon scripts; Build, Mod import, and switch preflight refuse exact script-path collisions found by bounded custom-content inspection. A saved SHA-256 of installed Valve weapon scripts warns when the source later changes or cannot be verified. Stock-art and HUD overlay notices describe installed candidates, never a confirmed in-game winner.
- **Viewmodels** — opens with In game controls: viewmodel FOV, Draw viewmodel, Min viewmodels, left-handed viewmodels and the Comfig transparent-viewmodels addon toggle (the same addon state as Comfig, disabled while TF2 runs or busy and outside Comfig profiles). The four cvars stay in `execs_gameplay.cfg` under a separate `viewmodels` managed-cfg scope that native `managed_cfg` and the frontend agree on, so Gameplay, Crosshair, Sounds and Viewmodels saves never rewrite each other's lines. They autosave like Gameplay and wait for a complete startup cfg read. Per weapon follows below. Every class… previews a whole-profile Show all, Hide all or Keep melee visible choice (Hidden or Hands only) as the exact list of rows that change, applies it only to the draft, and offers Undo until the next edit; melee inspect rows count as melee and shared-animation conflicts are disclosed before applying. It builds `tf/custom/execs-viewmodels.vpk` locally from the player's installed class animation MDLs: per-weapon Shown / Hidden / Hands only choices grouped by class slot and inspect, derived from installed sources without CompVMInstaller data. Build is available in release builds; the owner signed off on the retail TF2 result on September 25, 2026 without rendered previews. Profile export carries the build recipe and output digest, never the generated model bytes; import rebuilds from the recipient's own install and refuses source differences. It also imports, replaces and removes a user-provided compatible VPK, and earlier Yttrium-style packs retain their saved bytes and options through profile switch and export/import; legacy build and preview commands fail before I/O. Do not copy CompVMInstaller's source archive or group table. Custom viewmodels on Valve Casual need the profile's `+exec` preload launch option (see Launch).
- **Sounds** — hit and kill sounds are exactly `tf/custom/execs-hitsounds/sound/ui/{hitsound,killsound}.wav` (the two names sv_pure exempts). Engine formats: 8/16-bit PCM or 4-bit MS-ADPCM at 11025/22050/44100 Hz; other WAVs are re-encoded, MP3-as-WAV refused. New choices are stock effects from the user's `tf2_sound_misc_dir.vpk` and the user's own WAV. The TF2Hitsounds and comfig.app remote catalogs and native fetch paths are retired; previously installed catalog WAVs stay playable, switchable and exportable from profile-owned bytes, but their baked boost cannot change without a newly provided source. The searchable library shows stock and user-provided sounds (yours first, then by name) and always chooses for one slot: a Hit sound / Kill sound switch, set by each slot's Browse, drives one Preview and one Use action per row ("Use [sound] for hits"). A selected Use stays focusable, and a row names the other slot when it holds that sound. There are no source filters or date/popularity sorts. **Boost** (0/6/12 dB, tanh soft clip) re-encodes a user-provided file louder because the engine caps `tf_dingaling_volume` at 1. A saved custom WAV remains dormant when a nonzero built-in effect plays, and Sounds offers Use saved sound; selecting the default file effect or explicitly removing or replacing the file clears it. `sound.cache` is deleted on apply. Sound CVars, autoexec wiring, WAVs and the hitsound record commit in one recoverable profile transaction. Accepted external managed WAV drift marks sound provenance changed until every old installed slot is replaced or removed; Sounds shows a repair warning. Sounds scans other mounted `tf/custom` packs for the two canonical virtual paths and reports candidate competitors and incomplete scans; it does not claim which file TF2 plays in-game.
- **Mods** opens on three task surfaces: **Browse**, **Custom packs**, and **Casual setup**. Browse uses GameBanana game id **297** through `Mod/Index` for listings and name search; `Generic_Name=contains,<term>`, a selected `Generic_Category`, and mature-off `Generic_ContentRatings=-` compose server-side. New is the default; Popular, Likes, Views, Updated and New preserve upstream order and map to `Generic_MostDownloaded`, `Generic_MostLiked`, `Generic_MostViewed`, `Generic_LatestUpdated` and `Generic_Newest`. Added and updated dates stay distinct, unavailable metrics remain unknown, and All-category totals are estimates because non-GUI excluded roots are filtered locally. GUI results include HUD subcategory routing and author-guided import for other GUI types; native Mods install refuses a GUI payload. Completion, not the visible row count, controls Next. Native and renderer caches are bounded with a ten-minute fresh lifetime; Refresh and Retry bypass both while preserving the request. Cards identify GameBanana explicitly, paging appears above and below results, and one Import mod flow accepts a VPK/archive or extracted folder. **Custom packs** holds `ModRecord`s over ordinary `tf/custom` packs, including accepted external packs; RAR and multi-part VPKs are refused with a message. **Casual setup** owns the itemtest preload cfg, gameinfo bypass, four direct-author addon choices, saved legacy cueki choices from an exact verified local `mods.zip` cache, and installed profile mods that carry `particles/*.pcf` as particle sources. ## Saving

- Files saves require the expected active profile, confirmed root, verified cfg layer and exact live/library source hashes under the write gate. Source checks repeat after transaction snapshots and before publication; reviewed saves project even unchanged library bytes to repair deliberately resolved live drift. New cfgs require absence in both live and library trees, portable collision checks and the existing detected user layer. Provided cfgs and non-UTF-8 files remain read-only; helpers receive no implicit startup exec line.
- Files is a lazy-loaded CodeMirror workspace. Its fixed-width source font and bounded editor scroll surface are Files-only design exceptions; auxiliaries disclose below the full-width editor and move keyboard focus when opened. In-memory edits remain allowed while TF2 runs, but Files always requires explicit Save. Document navigation retains all session drafts, history, selection and scroll. Source conflicts require review; acknowledged hashes come from the committed manifest, never a later reload. Worker identity binds analysis to all draft revisions; timeout, crash and exhausted computation budgets refuse saves, while successfully analyzed unresolved runtime sources retain personal-config warning policy.
- Files separates syntax/safety/analysis Issues from offline command Catalog gaps, but shows Catalog gaps only in development builds; an uncatalogued command alone does not prove the cfg is invalid. Startup inference still refuses unknown commands whose side effects could change derived settings, points to the first cfg path and line, and suggests a known command when the spelling is close. A malformed individual bind is reported without discarding later known startup settings; UTF-8 BOMs are encoding metadata. Binds, Gameplay, Crosshair and Sounds label their inspected startup state and link direct Launch `+` commands and class CFG lines that may change it; launch command timing remains unverified in retail TF2. Help offers searchable command Details from the pinned reference and explains its evidence limits.

- Gameplay, Viewmodels, Crosshair and Sounds explain each startup value from the bounded resolver: final file and line, origin (execs, config.cfg, user cfg, HUD, pack, comfig import) and class cfgs that set it again, each opening in Files. A probe of the execs managed cfg reports later startup lines that override it; nothing is claimed when the resolver is incomplete or the managed cfg is not executed. The panel is read-only and never shows credential commands.
- Files drafts belong to the application session, keyed by profile and path. Closing execs, profile/install changes, profile creation and update installation ask Save / Discard / Cancel; Save awaits every dirty file and refuses the transition on failure, a changed profile, newer edits or the write lock. Files editing waits for the native close listener; host unmount alone never deletes drafts.
- Pending settings register their pane and awaited save with the session draft registry. Native close flushes unlocked autosaves; Files retain their explicit Save / Discard / Cancel decision. Failed, locked and unapplied drafts stay open with explicit discard/cancel and a route to their pane. Discard resets only affected panes from persisted props and suppresses their unmount flush; real writes must finish first. Settings editing waits for the native close listener.
- Launch TF2 names pending or failed settings and offers Review changes. Writes, switch/preloader recovery, Steam verification and update work retain their own guards and reasons; dismissing feedback never releases them.

Cvar and small-file panes autosave (`useAutosave`: 700 ms debounce, coalesced, deferred while TF2 runs, flushed when the lock lifts or the pane changes). Binds and Gameplay autosaves update controls quietly while writes run in the background; failures still report. Other writes use one toast: "Saving…" only past 400 ms, a named pane completion for a fresh 1600 ms, and a source-owned failure that stays until its own operation succeeds or is dismissed. "Draft kept until TF2 closes" appears briefly once for each locked draft; pending draft tracking and transition guards continue after the notice fades. Background reads clear only their own failures; dismissal never changes draft, recovery or write-lock state. Controls stay live while TF2 runs. Heavy or destructive actions keep a button that says what happens: Build pack, Apply mods, HUD install/update/import, Files Save/Discard, Remove pack, Remove sound files. No "packages installed" style status text when everything is fine.

Playbook: `docs/RELEASE.md`. Users install published GitHub Releases only. `main`, Linear, and draft / `workflow_dispatch` builds are private development. No nightlies, no public prereleases, no "try this build."

Inventory remains development-only and outside this release commitment. Update offers and native installation identity follow the newest completed successful check; a successful no-update result clears the offer, a failed check preserves the last successful offer, and obsolete checks cannot publish an identity after releasing their resource. Durable maintenance preflight failures show a copyable native error before the webview, background poller or command writers start; the version and state location remain visible and recovery markers are never cleared by that error path.

Versioning is `0.Y.Z` until a yearly review promotes 1.0.0. Patch (`0.Y.Z+1`) releases are bugfix-led, not bugfix-only: fixes are the default scope, but when the owner explicitly assigns a bounded, non-breaking feature or polish item to a named patch, that instruction defines the update. Record the exception in the milestone and keep older profiles and exports readable; additive internal recovery metadata remains allowed. Patch releases ship anytime — same day for install, updater, data-loss, or write-lock breaks. Minor (`0.Y+1.0`) is the monthly train (first Thursday, skip if empty): at most three planned user-visible features, or one large feature that is the whole release; profile and write-surface changes stay additive. Breaking changes (new write targets, unreadable profile/manifest, updater URL/key, dropped OS) need a minor and a `Breaking:` changelog line. Never put a breaking change in a patch.

When the owner explicitly requests a hotfix retaining the public product version, use a positive numeric build revision `X.Y.Z+N` (`1..65535`) in all four version files, the changelog heading, signed updater feed and a new immutable `vX.Y.Z+N` tag. Ordinary UI shows `X.Y.Z`, with `Hotfix N` where useful; diagnostics and update/release-note identities retain the full revision. The pinned Tauri updater compares Rust semver total ordering, including numeric build metadata; release probes verify old-to-hotfix discovery and no repeat offer after installation. Do not overwrite a published tag or its assets. Publish the verified hotfix as the latest stable release on the existing updater URL and signing key.

Private `workflow_dispatch` candidates require the matching `vX.Y.Z` input. Candidate and tag runs for that product version share one concurrency lock because both mutate the same draft. Installer smoke derives the immediately previous public version from ordered changelog history and tests that exact updater path; it is never hard-coded to an older release.

Release verification accepts GitHub's temporary `untagged-...` draft browser slug only when it matches that draft's `html_url` and the feed references its stable API asset URL. The exact `tag_name`, revision and signatures remain mandatory. Previous-installer downloads select actual public asset names, including either literal or normalized numeric build suffixes.

**Release handoff:** A release request is complete as soon as the authorized tag workflow has published the stable release and the public release, updater feed, signatures and provenance have passed the required verification. ## Gotchas worth remembering

- On Windows, launching the dev executable directly from packaged Codex can inherit its MSIX AppData virtualization and mix real profiles with `OpenAI.Codex_*/LocalCache/Roaming/execs` copies. Launch through the existing Explorer desktop's `Document.Application.ShellExecute` instead; confirm `GetPackageFullName` returns `APPMODEL_ERROR_NO_PACKAGE` (15700). Keep profile containment checks intact and do not merge or delete either library to work around this launch-context problem.
- Windows atomic file replacements and HUD backup moves pass absolute verbatim paths to `MoveFileExW`; `longPathAware` alone does not lift MAX_PATH when the system long-path policy is disabled. Preserve containment checks and resolve only endpoint parents so absent destinations and leaf rename semantics remain supported.

- Linux AppImages use the host Wayland libraries with the host EGL drivers. The before-bundle hook installs a project-local output plugin wrapper that removes only bundled Wayland libraries after deployment and before packaging/signing; keep the artifact check in installer smoke.

- Viewmodel compiler launches use Windows `CREATE_NO_WINDOW`; redirecting stdout/stderr alone still flashes a console for each class.

- Launching the real game for a test must not pass video flags (`-w`, `-h`, `-windowed`, `-noborder`, `-fullscreen`, `-dxlevel`): Source persists them into `HKCU\Software\Valve\Source\tf\Settings`. `-condebug` is fine; `-console` persists `con_enable`.
- An isolated `-game` directory does not isolate Steam Cloud: retail TF2 can still overwrite the account's `440/remote/cfg/config.cfg`. Do not use it as a player-state sandbox. Keep native verification in disposable core fixtures unless Cloud isolation is independently established; any approved real-game test must retain exact original bytes as well as hashes before launch.
- `C_OP_RenderSprites::RenderUnsorted … unimplemented sprite renderer` console floods mean a particle system whose material failed to load, not a PCF bug.
- comfig.app's CDN challenges empty or bare-library user agents; our UA string is enough.
- GameBanana's `Generic_LatestAdded` sort does not exist (`Generic_Newest` does); listings carry no download counts.
- Linux clippy flags imports used only by `#[cfg(windows)]` tests: import inside the test fn.
- Bash heredocs in the agent environment mangle backslashes; write patch scripts to a file first.
- **Branches:** keep `main` as the default development branch. Every other branch starts with `rndaom/`, never an agent/tool prefix. `rndaom/release-0.1` is the shared 0.1 maintenance line; use `rndaom/release-X.Y.Z` for a release candidate and `rndaom/forwardport-X.Y.Z` to carry its fixes into main. During 0.2.0 cleanup, draft PR #60 remains the integration PR against `main`; bounded cleanup PRs branch from and target `rndaom/foundry-overhaul`, then merge there after their own review and checks. Topic branches are temporary and are removed remotely after integration; immutable `vX.Y.Z` tags retain published release history.
- **Commits:** use the repo git identity (`Random`, not `Cursor Agent`). **Never add `Co-authored-by` trailers** — not for the owner, not for Cursor, not for any agent. At the start of every agent session run `git config --local core.hooksPath .githooks` (repo hook strips co-authors) **and** `chmod -x` the Cloud Agent file `commit-msg.cursor.co-author` under the VM's managed hooks dir. If a co-author line lands anyway, amend or rebase it out before push.
- User-facing changes add a `CHANGELOG.md` `[Unreleased]` line in the same commit.

## 0.1.5 cfg integrity

- Cfg safety scanning includes dormant files and bind/alias payloads without changing derived settings. Settings evaluate only known startup entry points and invoked exec/alias chains in order; definitions do not execute their payloads, and executed unbind operations remove bindings. A shared command/exec budget bounds both passes; incomplete execution blocks derived settings writes while Files remains available.
- Loose cfg startup and exec resolution uses immediate non-dot `tf/custom/<pack>/cfg` roots in case-insensitive ASCII mount-name order before `tf/cfg`; nested inactive/backup cfg folders do not become mounts. Case-colliding or unsupported mount order refuses inference. Derived saves stay blocked when a pack shadows the managed startup or settings files because native saves never rewrite provided packs.
- A legacy manifest with multiple HUD roots and HUD cfg files does not establish which cfg trees project live. Derived settings remain blocked with Save current as… recovery until a complete mounted setup is captured; Files stays available and no frontend HUD projection is guessed.
- Gameplay preserves `viewmodel_fov` throughout Source's 0.1–179.9 range without rounding incoming decimals. The viewmodel slider selects whole numbers once moved; it does not rewrite a fractional value loaded from cfg until that control changes. World FOV retains its separate 54–90 control.
## 0.1.5 pack and cfg integrity

- HUD option apply stages the whole tree before publishing. Resource edits preserve untouched text spans and BOM/legacy bytes; logical `Resource/*.res` and `Scripts/*.res` include headers must be unambiguous. Folder choices use portable validated moves, and schema expressions resolve from one complete option/default snapshot without executing code.

- A leading dash is part of a custom pack's literal identity. Absorb, Keep, removal and switch cleanup never substitute a dashed/undashed peer. Legacy HUD backup recovery requires a recorded inactive undashed HUD, no live undashed peer and no manifest ownership of the dashed path; coexisting or unknown dashed HUDs keep their normal identities.
- Cfg-layer detection reads the mounted startup autoexec and core cfg through one bounded content check. The supported mastercomfig loader executes `comfig/comfig.cfg` followed by `overrides/autoexec.cfg`; addon names and leftover overrides are not loader evidence. Inventory preserves safe nested user cfgs and overrides in both layers. Managed binds/gameplay writes refuse a live/library loader mismatch until the external change is resolved.
- Cfg inventory handles `user`, `app`, and `overrides` specially only when they are immediate `tf/cfg` children. The same names deeper in a user cfg tree remain literal profile content.
