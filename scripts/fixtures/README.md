# Package smoke profile fixture

`package-smoke-v021.json` retains the exact parsed export manifests and base64 payloads of the `no-hud` and `single-hud` archives the unmodified public **v0.2.1** core exported (tag `v0.2.1`, commit `ebb2d507635f314675a481a0c8b5d683fb4502cf`). They are copied from [`windows-package-v021/fixture.json`](windows-package-v021/fixture.json); that folder's README, `generation.json` and `harness/` record how the exports were made, and it retains both ZIPs unchanged. Each source archive's SHA-256 is recorded in the JSON, the manifests equal the `execs-profile.json` inside those ZIPs, and every payload hash was checked.

These are synthetic user cfg, mod and HUD payloads created by that public core; the VPKs were generated by its actual VPK writer. No Valve or third-party artwork, sounds, player secrets, account data or real profile library is included. The payloads deliberately match the earlier v0.1.8 compatibility cases.

The smoke fixture helper authors the on-disk index, profile IDs/names, confirmed settings and disposable TF2 root. Those structures are deliberately distinguished from the tagged-export bytes. It supplies one active profile and one inactive HUD profile, with ordinary mod records, launch options and a shared base VPK.

This small fixture holds everything the installer smoke test needs. It refuses to run unless the fixture exporter tag matches the immediately previous public version derived from changelog history. Refresh the fixture from actual exports of that version for a later release; do not simply change the tag string or reuse older bytes while calling them a newer export. Preserve archive hashes, payload hashes and the distinction between exported and authored structures.

The previous `package-smoke-v020.json` (v0.2.0 exports, used for the 0.2.1 release) is in Git history; its source archives remain in [`windows-package-v020`](windows-package-v020/README.md). The earlier `package-smoke-v018.json` (v0.1.8 exports, used for the 0.2.0 release) and its source archives are in Git history too.

The current-public capability checks (the Windows package probe and the Linux development package job) use a separate baseline: [`windows-package-v022`](windows-package-v022/README.md) holds authentic exports from the unmodified public **v0.2.2** core, and [`development-package-v022.json`](development-package-v022.json) pins its signed Linux packages. They follow the GitHub "Latest" release, while this release-upgrade fixture follows the immediately previous public version. The next release (0.2.3) refreshes this fixture from `windows-package-v022`, as 0.2.2 did from `windows-package-v021`.
